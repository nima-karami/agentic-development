# Translating Correct Specs into High-Quality UI with AI Agents

## The spec-to-quality gap

Your core framing is mostly right: a feature spec defines **correctness constraints** while good UI depends on additional judgments that are only partially representable as propositional text. Recent UI-agent benchmarks make that distinction unusually clear. VISTA explicitly evaluates agents on both functional behaviour and visual fidelity and finds that **visual fidelity and functional correctness are partially decoupled**, even when agents work from screenshots or Figma-derived structure rather than text alone. In other words, “meets requirements” and “looks/feels well-designed” are separable outcomes, not different names for the same thing. citeturn36view0turn36view1turn36view2

The evidence also suggests one refinement to your model: the three missing ingredients are real, but they only become operational when they are grounded in **explicit design context**. Figma’s own 2025–2026 material argues that design systems, tokens, shared patterns, and component libraries act as the “lingua franca” between design and AI, and that giving agents that context improves alignment and code output. Without that context, agents are left to interpolate from generic training patterns. citeturn16view4turn35search2turn35search3

What the functional spec leaves underdetermined is not trivial polish. It leaves open the very decisions professional designers spend most of their time on: **visual hierarchy, grouping, density, alignment, whitespace, emphasis, defaults, disclosure, legibility, motion, and tone of voice**. UICrit’s critique taxonomy surfaces the same pattern: major design issues repeatedly cluster around layout, visual hierarchy, contrast, readability, button emphasis, spacing, and learnability rather than missing requirements. citeturn30view2turn30view3turn30view4turn30view5

So the corrected model is this: **good UI needs a quality target, a translation layer, and a quality-verification loop — all grounded in concrete design context**. The quality target answers “what kind of good are we aiming for?”, the translation layer turns spec truths into hierarchy/form/composition decisions, and the verification loop judges the rendered result rather than assuming code completion implies design quality. Research on semantic intermediate representations for UI generation reaches the same conclusion: users struggle to express intent and evaluate outcomes, and systems become more predictable when semantics are made explicit and inspectable between prompt and output. citeturn37search0turn26search0

## The translation protocol

The most effective agent protocol is not “spec → code.” It is **spec → quality target → intermediate design artifact → implementation → rendered critique → revision**. That sequence is better aligned with both current academic results and the best documented product workflows from Figma, v0, Stitch, and recent HCI systems. Figma now explicitly describes a workflow where an agent first generates **design layers to clarify flows, states, copy, and structure**, then code layers to clarify behaviour. v0’s Figma guidance similarly recommends decomposing designs into smaller components, refining them in isolation, and only then composing them into full layouts. citeturn6view6turn35search3

A practical per-feature protocol that you can encode as an agent skill looks like this. First, extract the **correctness envelope** from the feature spec: user goals, permissions, states, empty/error/loading cases, edge cases, and success criteria. Second, define the **quality target** in a compact machine-readable design brief: audience and usage context, desired density, desired tone, reference exemplars, design-system scope, and the single most important behavioural outcome for the screen. Tools and research are converging around this need for explicit intent and reference conditioning: Google’s Stitch supports prompt-plus-image UI generation with theme selectors and iteration; example-driven systems such as \sys show that traceable examples help users articulate intent and justify design choices; Figma’s design-system context and v0’s design-system workflows both aim to improve fidelity by narrowing the output space. citeturn6view8turn16view1turn16view4turn35search2

Third, require an **intermediate design artifact** before any markup is written. The best artifact is not a loose wireframe alone and not a finished mock alone; it is a compact **hierarchy-and-layout specification** that forces design thinking. It should contain: the screen goal; the ranked priority of regions and actions; the page zoning or grid; the chosen focal point; primary vs secondary action treatment; progressive-disclosure rules; defaults; component-composition plan; copy/tone notes; and a state matrix for loading, empty, error, success, and permission variants. This recommendation is strongly supported by recent work: PrototypeAgent reports better quality and diversity by letting designers refine intermediate guidance and components rather than only end results; “Bridging Gulfs in UI Generation through Semantic Guidance” argues that an explicit semantic representation between human intent and UI output improves control and interpretability. citeturn26search0turn37search0

Fourth, implement against the design system, not against generic HTML taste. Fifth, render **all meaningful states with realistic data**, not placeholder ideal states. Figma’s published workflows repeatedly emphasize this: teams found that flows that “looked right” in a static direction fell apart when real data, permissions, and task sequences were exercised; bringing coded states back onto the canvas exposed missing recovery paths, weak loading feedback, empty states, and unsupported-format cases that the initial direction had not resolved. citeturn6view7turn16view3

Sixth, run screenshot critique and deterministic linting. Seventh, revise until the UI clears both correctness and quality bars. The correct stopping rule is not “the agent says it’s done”; it is “deterministic checks pass, the judge finds no severe issues, and the latest version no longer wins convincingly over the previous one in blinded pairwise comparison.” Pairwise comparison is important because judge models are more reliable in pairwise settings than in scalar scoring, and self-preference bias is now well documented. citeturn29search0turn29search2turn29search3turn29search15

## Why agents regress to generic UI

LLM agents tend to produce mediocre UI for three distinct reasons. The first is **distributional averaging**. Generative models are trained to produce outputs that resemble their training distributions, and recent statistical work argues that generative systems are inherently prone to “regression toward the mean,” shrinking variance relative to real human output. In design terms, that means the model drifts toward competent-average solutions and away from distinctive, opinionated ones. citeturn12search1turn12search8

The second is **satisficing after requirement satisfaction**. Once the spec is functionally met, the generator has no strong incentive to keep searching for a better hierarchy, better rhythm, or stronger emphasis unless the workflow explicitly defines a quality bar. AlignUI makes this concrete: without user-preference grounding, generated controls become generic; with preference data injected into reasoning, outputs align more closely with predictability, efficiency, and explorability as judged by users. citeturn27view1

The third is **skipping the design step**. End-to-end generation systems often still behave as if UI creation were “prompt in, markup out,” but recent UI-generation research keeps arriving at the same failure mode: limited support for iterative intent clarification, weak transparency, and not enough structure for refining intermediate choices. PrototypeAgent and related work explicitly frame the issue as a lack of support for iterative generation and intermediate refinement; semantic-guidance work frames it as a gap between user intent and interpretable outcome. citeturn26search0turn26search2turn37search0

The mitigation stack is therefore fairly direct. Give the agent a **quality target** that names the desired density, tone, hierarchy style, and exemplars. Give it **design-system constraints** so it has a branded grammar rather than generic component soup. Force an **intermediate hierarchy artifact** before code. Use **real data and full state coverage**. Judge via **separate critique passes**, ideally with a different model from the generator, and compare versions pairwise rather than relying on self-scored absolute ratings. Multi-perspective critique also helps: CritiqueCrew reports improved design quality and subjective experience over a static checker by orchestrating distinct UX, PM, and engineering perspectives instead of collapsing everything into one undifferentiated review voice. citeturn16view4turn6view6turn16view3turn38search0turn38search6

## The rubric and critique loop

An agent-runnable quality rubric should judge the **rendered screen** along six dimensions. This is a synthesis of UICrit’s issue clusters, Nielsen’s heuristics, accessibility standards, and newer aesthetics benchmarks such as AesEval-Bench. The key point is that the judge must evaluate both broad screen quality and *localized* defects, because modern benchmarks increasingly test not just aesthetic judgment but also region selection and precise localization. citeturn30view2turn23search0turn31view0

Use this rubric for screenshot critique:

- **Purpose and focal point.** Can the judge tell within a few seconds what the screen is for and what to do next? Is there one clearly dominant task path, or are multiple elements competing for attention? UICrit repeatedly flags poor visual hierarchy, unclear UI purpose, and misplaced primary actions as quality failures. citeturn30view2turn30view3  
- **Hierarchy and emphasis.** Are importance levels visibly encoded through size, contrast, spacing, placement, and action treatment? Material explicitly recommends one high-emphasis button for the primary action on a screen; UICrit likewise identifies weak button prominence and weak interactive emphasis as common problems. citeturn18search1turn18search9turn30view2turn30view3  
- **Rhythm, spacing, and alignment.** Does the screen read as an intentional system rather than a pile of boxes? Check grouping, evenness, edge alignment, white-space use, and density consistency. UICrit’s layout cluster and Apple’s basic UI guidance both treat alignment and spacing as first-order design signals. citeturn30view2turn30view3turn21view2  
- **Legibility and contrast.** Is text easy to scan, large enough, and supported by sufficient contrast? WCAG 2.2 requires 4.5:1 contrast for normal text and 3:1 for large text; Apple advises at least 11-point text and warns against overlap and poor spacing. citeturn5search3turn5search6turn21view2  
- **Affordance, feedback, and microinteraction clarity.** Do interactive elements look interactive? Are defaults, loading, success, and failure states understandable? Apple’s motion guidance emphasizes brief, precise feedback, and Heuristic Evaluation research consistently finds visibility of status, consistency, and labels easier for models to judge than more aesthetic concerns. citeturn17search3turn23search0turn14view1  
- **Restraint and tone.** Is the screen appropriately edited? Is the copy concise, plain, and consistent with the intended tone? Apple’s writing guidance stresses simple, conversational, helpful language; NN/g’s minimalist-design heuristic remains relevant here. citeturn21view10turn19search6turn23search0

The critique loop should be tight and adversarial. Render the screen, then ask a **separate judge** to identify the top three strengths, the top five issues, a severity for each issue, the implicated region, and the smallest plausible fix. Do not ask “is this good?” Ask “which version is better, why, and where are the defects?” Pairwise comparisons are more robust than scalar scoring, and same-model judging risks self-preference bias. citeturn29search0turn29search2turn29search3turn10view3

A practical prompt template is:

```text
You are evaluating a rendered UI screenshot against a quality bar, not checking whether the feature spec was implemented.

Inputs:
- Screenshot of current screen
- Quality target: [brand adjectives, density target, tone, exemplars]
- Screen intent: [primary user goal + primary action]
- Design-system constraints: [tokens/components allowed]
- Optional comparator screenshot: previous version

Tasks:
1. Decide which version better satisfies the quality target.
2. Score the current screen 1–5 on:
   - purpose clarity
   - visual hierarchy
   - spacing/alignment rhythm
   - readability/contrast
   - affordance/feedback
   - restraint/tone
3. Identify up to 5 issues only if they are materially important.
4. For each issue, provide:
   - severity: blocker / major / minor
   - region: describe exact area
   - evidence: what in the screenshot caused the judgment
   - fix: one concrete revision
5. Do not reward completeness or effort. Judge only the rendered quality.
6. If uncertain, say uncertain.
```

In practice, cap autonomous critique loops at roughly **two or three passes**. That is an inference from current evidence, not a hard law: automated critique is useful early, but the Berkeley/Figma-style heuristic work found that critique quality falls as interfaces improve, producing more false positives in later rounds. Past that point, either switch judges, switch to pairwise challenger reviews, or involve a human. citeturn14view0turn14view1

## Encodable heuristics and CI checks

The most valuable “craft knowledge” for an agent is the subset that can be made explicit, measurable, and repeatable. Some of it comes from standards; some of it is a house style you should encode as defaults. The goal is not to automate taste away, but to raise the floor so the judge loop is spending time on genuinely visual problems instead of preventable sloppiness. citeturn34search1turn16view4

The strongest **deterministic checks** are these. Enforce WCAG contrast minima for text and non-text elements; enforce touch-target minima appropriate to the platform; enforce design-token adherence for colors, type roles, spacing tokens, corner radii, and component use; detect overflow, overlap, clipping, missing labels, and state-specific layout breakage; and check that primary/secondary action treatment follows policy. Official minima are clear: WCAG 2.2 sets 4.5:1 for normal text and 24×24 CSS pixels for web targets at AA; Apple recommends at least 44×44 pt touch regions and at least 11 pt text; Material recommends at least 48×48 dp touch targets and strongly prefers a single high-emphasis primary action per screen. citeturn5search3turn20search15turn20search3turn21view2turn20search2turn20search18turn20search1turn20search25turn18search1

The most useful **encodable craft heuristics** beyond standards are best treated as house rules. Good defaults are: one dominant primary action per screen; no more than one focal region above the fold; a discrete spacing scale rather than ad hoc pixel values; fixed type tokens rather than arbitrary font-size drift; explicit density targets by screen type; progressive disclosure for forms and advanced settings; defaults chosen to reduce work and educate expectations; motion used only to clarify causality, hierarchy, or feedback; and copy that is plain, direct, and action-oriented. These recommendations are consistent with NN/g’s guidance on defaults and progressive disclosure, Apple’s motion and writing guidance, Material’s typography/spacing systems, and UICrit’s taxonomy of common failures. citeturn17search0turn17search1turn17search7turn17search9turn17search3turn19search16turn21view10turn5search0turn5search4turn5search13turn5search28turn30view2turn30view3

The important split is this. **Deterministic CI can prove conformance** to accessibility, token use, spacing/value systems, target sizes, presence of states, and many structural/layout defects. But **vision or judgment checks are still required** for focal strength, whitespace rhythm, whether something feels cluttered or too sparse for its task, whether one CTA is over- or under-emphasized, whether the screen has restraint, and whether the overall composition looks generic rather than intentional. Current research supports that split: display-defect detection and some heuristic checks are becoming tractable, but nuanced UI/UX reasoning, behavioural prediction, and aesthetic assessment still show clear gaps. citeturn10view0turn10view1turn10view5turn31view0

## The 2026 state of the art

The established part of the 2026 picture is this: AI can now generate working, often high-fidelity interface drafts; it can critique static screens with useful-but-imperfect feedback; and it can be materially improved by designer feedback, design-system context, and structured iteration. Apple reports that designer-aligned feedback methods such as commenting, sketching, and direct manipulation outperform ranking-only feedback and produce higher-quality UI generation models. Figma’s 2026 workflow material shows agents working directly on the canvas, generating layout variations, design layers, and code-connected states. Google Stitch generates UI from natural language, screenshots, and wireframes; v0 and Lovable both operationalize fast preview/edit/iterate loops with design-system or visual context. citeturn13view0turn14view4turn6view6turn6view7turn16view3turn6view8turn35search0turn35search1turn6view9

The established research finding is more cautious than the tooling hype. Automating UI quality assessment is improving, but it is not solved. UICrit shows meaningful gains from critique datasets and localized prompting, yet still states that current LLM-based UI evaluation does not match human evaluators. The earlier CHI work on automatic feedback found GPT-4 more accurate/helpful than not on poor UIs, but weaker after iterative improvement and limited to single static screens. MLLM-as-a-UI-Judge reaches only about **60% overall accuracy** on pairwise human-preference prediction in its benchmark. UXBench reports that mainstream MLLMs remain fundamentally limited on fine-grained UX reasoning. UI-Lens shows near-random performance on several fine-grained defect categories such as text overflow and overlap. AesEval-Bench, from Microsoft Research, frames graphic-design aesthetics assessment as central but still underexplored, with clear performance gaps for current VLMs. citeturn7view4turn7view5turn14view1turn14view2turn10view3turn10view1turn10view0turn31view0

The emerging and still-contested frontier is **quality-aware generation**, not just quality-aware evaluation. Current work is pushing in several promising directions: user-preference conditioning rather than generic prompting; semantic intermediate representations; multi-perspective critique; example retrieval and remix rather than raw generation; and agent loops that move between code and canvas instead of staying in one modality. AlignUI improves preference alignment by guiding reasoning with user-preference data; CritiqueCrew improves quality and trust through role-orchestrated critique; semantic-guidance work argues that explicit design semantics bridge both the execution and evaluation gulfs; example-driven systems help users articulate otherwise tacit taste through traceable references. citeturn27view1turn38search0turn38search6turn37search0turn16view1

Open questions remain. The field still lacks a proven, general-purpose judge that can reliably assess close aesthetic calls, brand distinctiveness, or behavioural effectiveness of subtle layout changes without human review. The best evidence for behavioural UI quality still comes from real A/B outcomes; WiserUI-Bench exists precisely because surface-level heuristic checks are not enough to capture how design guides user behaviour. And current judge systems are vulnerable to bias, including self-preference bias and position bias, which means any production verify harness should treat AI critique as **decision support**, not final authority. citeturn10view5turn29search0turn29search3

The practical conclusion is straightforward. In 2026, agents can absolutely help you move from correct specs to better interfaces, but only if you stop treating UI as a direct code-generation task. The winning pattern is: **declare the quality target, force a translation artifact, render real states, run deterministic lint plus adversarial screenshot critique, revise in short loops, and reserve final judgment on close aesthetic or brand-sensitive decisions for humans**. That is the highest-confidence workflow the evidence currently supports. citeturn36view1turn37search0turn14view1turn16view4turn27view1
