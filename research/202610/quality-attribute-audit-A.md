# **Comprehensive Codebase Audit Dimensions: Security and Performance in Agent-Generated Systems**

The systematic evaluation of existing codebases—particularly those substantially generated and maintained by autonomous coding agents—requires transitioning from generalized best practices to rigorously tailored, profile-driven rubrics. The audit dimensions of security and performance cannot be evaluated in a vacuum; a critical architectural flaw in a multi-tenant financial service may represent an entirely acceptable trade-off in a single-user local desktop utility. To bridge the gap between static mechanical extraction and contextual human or model-driven judgment, an audit relies on a fixed methodology: deterministic tool extraction, alignment with a written rubric, model judgment on the candidates, and fresh-context verification.  
This report establishes the exhaustive criteria, deterministic tooling, and analytical frameworks required to evaluate the security and performance dimensions of an as-built codebase, with specialized attention to the unique failure patterns introduced by modern (2025–2026) LLM coding agents.

## **The Minimal Codebase Profile**

Before either dimension can be judged deterministically, the audit requires a precise minimal profile. Without these facts, an auditor cannot differentiate between deliberate architectural simplification and critical vulnerability. The minimum profile must explicitly declare the following parameters.  
The deployment model and platform dictate the attack surface and baseline processing power. The profile must distinguish between an edge-deployed serverless function, a stateful persistent backend, a desktop Electron client, or a mobile web interface. The target load and capacity must be numerically defined. Establishing whether the system expects 2,000 internal concurrent users or 100,000 global connections determines whether a missing database index is a theoretical inefficiency or a critical Denial of Service (DoS) vulnerability.  
The data sensitivity and stakes fundamentally alter the severity of logging and authorization findings. The profile must classify the data as transient anonymous state, regulated financial records, or proprietary corporate intellectual property. Network and device constraints establish the performance budgets. A profile targeting broadband desktop environments allows for fundamentally different bundle sizes and JavaScript execution times than a profile targeting low-end mobile devices operating on congested 4G networks. Finally, the authentication and trust model must be established. The audit must know whether all users operate as trusted insiders within a secured intranet, or if the architecture is a multi-tenant public Software-as-a-Service (SaaS) demanding rigorous tenant isolation.

## **Translating Profiles to Audit Criteria**

The translation of a system's quality attributes and context into concrete audit criteria relies on established architectural evaluation frameworks, primarily the Architecture Tradeoff Analysis Method (ATAM) developed by the Software Engineering Institute (SEI)7. ATAM mandates the creation of a utility tree, which decomposes high-level quality attributes (security, performance) into testable, localized scenarios. A quality-attribute scenario specifies a source of stimulus, environmental conditions, and a measurable response10.  
For example, a profile indicating "100k concurrent players" on a real-time multiplayer backend translates into a performance scenario: under peak load (environmental condition), a player state update (stimulus) must be broadcast to all relevant session peers within 50 milliseconds without exceeding 80% CPU utilization on the node (measurable response). This scenario explicitly dictates the criteria for the audit's static analysis phase: the codebase must utilize push-based WebSockets rather than HTTP polling, and the data structures managing peer connections must scale with ![][image1] or ![][image2] complexity. If the static reading reveals an ![][image3] array iteration for message broadcasting, it becomes a high-severity finding directly tied to the capacity target.  
For performance budgets on web platforms, the profile constraints strictly enforce standardized industry metrics. If the profile targets consumer web users, the audit relies on the 2026 Core Web Vitals (CWV) thresholds. The audit strictly evaluates whether the architecture can achieve a Largest Contentful Paint (LCP) under 2.0 seconds and an Interaction to Next Paint (INP) under 200 milliseconds5. The profile's device class acts as the severity multiplier: a 500KB JavaScript bundle loading on a desktop may process in 200ms, satisfying the budget, but the same bundle on a low-end mobile device will require 800ms to 1.2 seconds, failing the budget catastrophically6.  
In the security dimension, threat modeling at audit time operates over the as-built code. Rather than generating hypothetical white-board models, the audit applies frameworks like STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) directly to the architectural trust boundaries extracted from the code12. The minimal profile dictates where these boundaries lie. If the system is a multi-tenant web application, the boundary exists between the incoming HTTP request and the routing layer. The audit criteria demand mechanical proof that data parsing and authorization verification occur precisely at this boundary.

## **Security in an As-Built Codebase**

Evaluating security within an existing repository involves dividing labor between deterministic mechanical extraction and model-assisted judgment. The NIST Secure Software Development Framework (SSDF) SP 800-218 emphasizes the necessity of automated code analysis alongside contextual review to continuously identify vulnerabilities (Tasks PW.7.2 and RV.1.2)12. Scanners excel at identifying structural anomalies, such as the use of deprecated cryptographic algorithms or the hardcoding of secrets. However, scanners frequently fail to comprehend business logic and domain-specific trust boundaries, generating false positives that obscure genuine risk.  
Trust boundaries and threat models require judgment aided by mechanical mapping. A scanner can identify all public API endpoints, but a fresh-context verifier is required to assess whether those endpoints adequately validate incoming payloads against the business requirements. Authorization placement presents a similar dichotomy. Mechanical tools can easily flag a route handler that lacks an authorization middleware decorator. Yet, verifying that the implemented authorization logic correctly binds the authenticated user to the specifically requested resource—preventing Insecure Direct Object Reference (IDOR)—requires an understanding of the database schema and ownership relationships that a simple static scanner lacks.  
Secrets handling and dependency posture belong almost entirely to mechanical scanners. Tools like TruffleHog utilize entropy analysis and pattern matching to extract cryptographic keys from git histories3. Supply chain security relies on manifest parsers (e.g., pip-audit, trivy) to cross-reference dependencies against known CVE databases14. However, the audit rubric must scale the severity of these mechanical findings using the codebase profile. A vulnerability in a development-only testing dependency carries negligible risk, whereas a remote code execution vulnerability in a core production web framework is critical.  
Process isolation and sandboxing require deep inspection, particularly in specific deployment profiles like Electron or mobile applications. In an Electron application, the audit mechanically verifies the explicit implementation of contextIsolation: true and the disabling of nodeIntegration. However, evaluating the Inter-Process Communication (IPC) bridge between the untrusted renderer and the privileged main process requires judgment to ensure that attackers cannot exploit the IPC channels to execute arbitrary shell commands on the host OS2.

## **Security Failure Patterns Specific to Agent-Written Code**

The rapid integration of Large Language Model (LLM) coding agents into development environments has introduced novel security failure patterns that traditional static analysis scanners frequently misinterpret. Empirical studies conducted across 2025 and 2026 demonstrate that while agents write functionally correct code, they routinely introduce and preserve specific classes of vulnerabilities due to their iterative execution models and default trust architectures.  
A primary vulnerability vector is "trajectory-level security debt." Agents operate over hundreds or thousands of interaction turns to complete complex tasks. Research analyzing agent trajectories utilizing the Security Debt Line Integral (SDLI) metric reveals that insecure design choices made in early execution checkpoints often persist throughout the entire repository history15. Because coding agents utilize their own earlier outputs as context for subsequent modifications, a temporary shortcut—such as disabling a CSRF protection to force a test suite to pass—becomes entrenched. Empirical analysis of AI-generated code across public repositories shows that 22.7% of security issues introduced by AI survive into the latest version of the repository without being refactored16.  
Furthermore, agent architectures introduce severe software supply chain vulnerabilities through "agent skills" and external tool use. Agents possess system-level execution privileges (file I/O, network requests, shell access) and inherently trust external instructions. Attackers exploit this via Data-Driven Indirect Prompt Injection (DDIPE). By embedding malicious logic within code examples, issue trackers, or configuration templates, attackers hijack the agent's action space1. Recent evaluations of DDIPE against leading agent frameworks demonstrated successful execution bypass rates ranging from 11.6% to 33.5% across various models4. These poisoned skills induce agents to execute payloads that bypass internal alignment guardrails.  
Two specific manifestations of agent-driven exploitation dominate the landscape. The first is "Persistent Execution via Hidden Validation Hooks." Agents are manipulated via poisoned documentation to create hidden shell scripts (e.g., .validate\_hnf.sh) disguised as local validation tools1. The script silently contacts an attacker-controlled endpoint and then runs the legitimate test suite to evade developer suspicion. The second manifestation is "Security Policy Bypass via Configuration Poisoning." Agents are instructed to modify framework-specific configuration files (such as .cursorrules or CLAUDE.md) to automatically bypass terminal confirmation prompts, effectively dismantling the agent's own safety scaffolding1.  
Standard SAST scanners struggle to detect these patterns because a hidden bash script executing a network request is structurally indistinguishable from a legitimate deployment script. Defending against agent-specific vulnerabilities during an audit requires implementing deterministic extraction limits that flag any modification to agent directive files, combined with fresh-context LLM verifiers trained specifically to analyze the behavioral intent of shell scripts and git hooks introduced during the agent's trajectory.

## **Performance Evaluation: Static Reading vs. Measurement**

Performance auditing operates across two distinct domains: architectural anti-patterns that can be deterministically extracted from static code, and runtime bottlenecks that require empirical measurement under simulated load.

### **Performance from Static Reading**

A significant proportion of performance degradation originates from code structures that scale geometrically with data volume or network latency. These can be audited purely from code, history, and build outputs without executing the system.  
The N+1 query pattern is the most universally damaging static finding. This occurs when a parent entity is retrieved from a database, and an iterative loop executes a separate database query for each child entity. While this executes rapidly during development with nominal data, it causes exponential latency degradation in production. Static analysis tools parse the Abstract Syntax Tree (AST) to identify ORM invocations nested within loop constructs.  
Similarly, unbounded lists and payloads represent severe architectural flaws. If an API endpoint or database query lacks explicit pagination—such as LIMIT clauses or cursor metadata—it will inevitably exhaust memory and network bandwidth as the system accrues historical data. Synchronous I/O on hot paths presents a critical static finding specifically for single-threaded asynchronous runtimes like Node.js and Python Asyncio. Utilizing blocking functions (e.g., fs.readFileSync) in a request handler stalls the entire event loop, queuing all concurrent requests behind a single slow disk operation17.  
However, reporting these static findings requires careful calibration against the codebase profile to avoid demanding premature optimization. Implementing complex cursor-based pagination for a configuration table structurally guaranteed to contain fewer than twenty rows is an exercise in over-engineering. The audit relies on the capacity targets defined in the profile: an N+1 query pattern in a nightly batch processing script carries low severity, whereas the exact same pattern in a user-facing social feed under high concurrent load represents a critical vulnerability.

### **Performance that Must be Measured**

Certain performance claims remain entirely speculative until measured. The execution duration of complex database joins, the accumulation of memory leaks, and browser layout thrashing depend completely on runtime environments, data cardinality, and garbage collection behaviors.  
The cheapest credible measurement strategy for an audit involves isolated profiling of representative flows rather than comprehensive distributed load testing. For backend services, wrapping a critical path with a lightweight profiler (such as py-spy for Python or async-profiler for the JVM) generates a self-contained interactive HTML flamegraph18. This artifact visually isolates the specific function monopolizing CPU cycles without requiring complex infrastructure. For web front-ends, static bundle analysis deterministically calculates asset weight, while browser performance tools like Lighthouse CI, configured with mobile CPU and network throttling, measure the core rendering bottlenecks19.  
When an audit identifies a highly suspicious static candidate—such as a deeply nested, recursive regular expression on user input—but lacks the infrastructure to measure it, the framework dictates reporting it as an "Unverified Architectural Risk." The finding must document the mechanical anchor (path and line), articulate the theoretical degradation path (e.g., catastrophic backtracking leading to ReDoS), and explicitly advise the engineering team to measure the function under targeted synthetic load before deployment.

## **Platform Specifics and Scaling Considerations**

The severity and applicability of audit criteria fluctuate radically based on the target platform and the anticipated scale. The codebase profile serves as the ultimate arbiter for severity scaling.

### **Web Front-Ends and Mobile Constraints**

For web applications accessed via mobile devices, network latency and restricted CPU processing dominate the performance rubric. A JavaScript payload that executes smoothly on a broadband desktop environment will frequently stall a mid-tier mobile processor operating on a congested 4G network6. The audit relies on the tightened 2026 Core Web Vitals thresholds. If the frontend architecture cannot demonstrably achieve a Largest Contentful Paint (LCP) under 2.0 seconds and an Interaction to Next Paint (INP) under 200 milliseconds, it constitutes a high-severity finding5. The audit must mandate edge caching, image optimization, and the deferral of non-critical JavaScript to satisfy these metrics6.

### **Desktop Applications (Electron)**

In the context of desktop applications built on web technologies (e.g., Electron), the audit focus pivots sharply toward process isolation and Inter-Process Communication (IPC) security. The severity of a Cross-Site Scripting (XSS) vulnerability escalates to a full Remote Code Execution (RCE) if the rendering process possesses native system privileges. The rubric strictly demands the mechanical verification of contextIsolation: true and nodeIntegration: false, alongside the rigorous sanitization of all data traversing the IPC bridge from the untrusted renderer to the privileged main process2. Performance checks for desktop apps deprioritize network latency in favor of memory footprint analysis, as memory leaks degrade the user's host operating system over prolonged uptime.

### **Real-Time Systems and Load Scaling**

The transition in the system profile from 2,000 concurrent users to 100,000 concurrent users fundamentally rewrites the architectural requirements. At 2,000 users, vertical scaling and basic database connection pooling can often mask inefficient queries or slight memory leaks. At 100,000 users, those identical inefficiencies trigger catastrophic connection pool exhaustion and localized memory starvation. In real-time systems, the audit must aggressively penalize polling architectures, demanding push-based synchronization mechanisms like WebSockets or WebRTC. Security checks must heavily prioritize state and concurrency integrity, ensuring that rapid concurrent operations (such as deducting virtual currency) enforce strict database locking or atomic increments to prevent Time-of-Check to Time-of-Use (TOCTOU) exploitation2.

## **Severity Calibration**

To systematically scale the severity of an audit finding based on the codebase profile, practitioners rely on established vulnerability scoring systems, specifically blending the Common Vulnerability Scoring System (CVSS v4.0) with the OWASP Risk Rating Methodology.  
CVSS v4.0 provides the objective technical baseline. It isolates the Base Metrics—the intrinsic qualities of a vulnerability that do not change across environments, such as the Attack Vector (Network vs. Local), Attack Requirements (AT), and the technical impact on Confidentiality, Integrity, and Availability23. CVSS v4.0 explicitly introduced the Threat Metric Group and improved the Environmental metrics to allow organizations to tailor the score based on compensating controls24. For instance, a Server-Side Request Forgery (SSRF) flaw inherently possesses a High Base score. However, if the system profile is a local desktop application with no outbound network access, the Environmental metric drastically lowers the final technical score.  
However, CVSS measures technical severity, not business risk. To determine the final audit severity, the CVSS score is filtered through the OWASP Risk Rating Methodology, which calculates risk as Likelihood × Business Impact26. The OWASP model forces the auditor to evaluate the profile's specific stakes. If a finding is technically severe (CVSS High) but exists within a batch processing script analyzing public weather data, the OWASP Business Impact is low, resulting in a moderate final audit severity. Conversely, a medium-severity technical flaw that exposes regulated financial data results in a critical final audit severity due to the extreme business impact26.

## **Verdict on Secondary Quality Attributes**

When establishing the dimensions of an audit, it is necessary to determine whether Reliability/Resilience, Accessibility, and Observability warrant independent rubrics, or if they are more effectively integrated into the primary architecture, security, and performance dimensions.  
**Reliability and Resilience** should be folded directly into the Performance and Architecture dimensions. Resilience mechanisms—such as circuit breakers, retry logic with exponential backoff, and rate limiting—are architectural patterns fundamentally designed to prevent systemic performance degradation under extreme load or downstream service failure. Establishing a separate dimension creates analytical redundancy. For example, database connection pooling acts simultaneously as a performance optimization and a critical reliability safeguard.  
**Accessibility (a11y)** merits its own standalone audit dimension if, and only if, the codebase profile mandates compliance with legal or institutional standards (e.g., WCAG 2.2 AA for government contracts, educational software, or mass-market consumer tools). Accessibility evaluation is highly deterministic, measurable by standardized tools like axe-core, and possesses a rigid set of rules (color contrast ratios, ARIA label accuracy, keyboard navigability) that do not overlap with security or performance criteria. If the profile indicates an internal developer utility or a backend microservice, this dimension can be safely omitted.  
**Observability** should be folded into the Security and Architecture dimensions. The presence of distributed tracing mechanisms, centralized logging, and health-check endpoints relates strictly to the operational architecture of the system. Concurrently, the integrity of audit logs—ensuring non-repudiation and validating the prevention of sensitive data leakage—constitutes a critical security parameter28. Observability does not generate a sufficient volume of distinct, code-level fault paths to justify a completely isolated audit rubric; rather, it functions as a critical mitigating control for the other primary attributes.
