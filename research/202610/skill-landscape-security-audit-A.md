# Existing skills for security analysis, codebase audits, and release readiness

## Bottom line

**Security analysis:** **Cloudflare `security-audit` — P3**, best overall fit for a file-loaded, vendor-portable skill; **adapt**, do not adopt unchanged. Its strongest proven ideas are independent validation, coverage ledgers, machine-readable findings, sandboxed execution, and human review. citeturn21search2turn21search6turn22view1  
**Security detection method:** **IRIS — P1**, the strongest reproducibly evaluated scanner/LLM composition found: 55/120 known Java vulnerabilities detected versus 27/120 for CodeQL alone, but it is Java/CodeQL-specific and still noisy. citeturn17view1  
**Scanner triage:** independently evaluated agentic triage is compelling but **must not auto-suppress findings**: the best 2026 study reached 95.5% FP precision/recall on post-cutoff cases while suppressing 22.25% of true OWASP vulnerabilities in a separate retention test. citeturn16view4turn17view0  
**Threat modelling/auth review:** no dedicated, general-purpose open skill reached P1–P3; Cloudflare and Trail of Bits contain the best reusable structures, but only Cloudflare has meaningful field evidence. citeturn21search2turn20search4  
**Whole-codebase architecture/quality/test-health/drift audit:** **nothing proven for the requested full scope**. RepoAudit is P1 for repository-level *bug finding*, not architecture erosion or test-health auditing. citeturn21search1turn6view0  
**Release readiness:** **OpenAI `final-release-review` — P3**, best actual skill; **adapt**. Pair its exact-candidate/human-approval mechanics with Kubernetes' P3 Production Readiness Review questions for operational readiness. citeturn19search2turn19search1turn14search7  
**Do not copy RepoAudit into a commercial delivery pipeline:** its current licence is explicitly non-commercial, despite older indexed copies showing MIT. citeturn22view0turn21search5  
**Overall decision:** adopt no candidate completely unchanged; build the in-house stages from a small number of evidenced mechanisms, then benchmark them against VulnGym/CWE-Bench and seeded release/codebase tasks. citeturn14search5turn15search2

## Evidence standard and search result

I applied the requested ladder literally. **P1** means the candidate has numerical comparison against a baseline *and* a runnable public implementation/harness; **P2** means a third party evaluated the candidate; **P3** is documented use on real work with outcomes; **P4** is adoption/activity only; **P5** means no qualifying effectiveness evidence. A candidate can have more than one kind of evidence; the table reports the rung most useful for the decision rather than treating stars as an upgrade. Popularity is noted only where it reveals maintenance/adoption, never as effectiveness.

All repository snapshots below were checked **October 27, 2026**. Where GitHub exposed both repository HEAD and the last commit touching a skill, I use the skill-specific commit because that is the reproducible artefact. Where the retrieved page did not expose an exact HEAD, I say so rather than invent one.

The main negative finding is important: in late 2026 there is substantially better empirical work for **security finding and SAST triage** than for **architecture-quality auditing** or **release-readiness agents**. Release readiness has unusually strong *field-process* evidence but little controlled A/B evidence. Holistic codebase auditing remains dominated by elaborate prompt packs with little or no outcome measurement. citeturn15search1turn18search3turn19search2

### What the measured systems actually say

**The strongest reproducible detection result is not “let the LLM audit the repository.” It is “let the LLM extend a deterministic analysis.”** IRIS uses the model to infer missing semantic information—sources and sinks—then lets CodeQL calculate interprocedural paths. On 120 validated Java vulnerabilities this moved detection from CodeQL's 22.5% to 45.83% with GPT-4. Ablating either the LLM source specifications or sink specifications substantially reduced detections. This is direct evidence for an agent-as-*specification generator* arrangement rather than an agent-as-final-oracle arrangement. citeturn17view1turn17view2

IRIS also shows the limitation: more recall does not make the final result trustworthy. Its headline Avg FDR remained 84.82%, and the separate manual sample produced an estimated 46% FDR. So the reusable lesson is **expand deterministic coverage with LLM judgement, but retain a second validation/reproduction stage before a human-facing “confirmed” finding**. citeturn17view1turn17view2

The best 2026 evidence for the reverse arrangement—**scanner first, agent second**—is Xiong and Zhang's *Sifting the Noise*. They independently evaluated Aider, OpenHands and SWE-agent on SAST alerts from OWASP Benchmark, Vul4J/CodeQL and post-cutoff OSS-Fuzz cases. On the post-cutoff C/C++ set, SWE-agent + Claude Sonnet 4 identified “**95.5% of FPs while maintaining 95.5% precision**”, versus 36.4% FP identification for vanilla prompting. Removing cross-file navigation dropped F1 from 95.5% to 62.5%; removing multi-turn interaction reduced it to 56.3%; removing tool-based verification reduced it to 88.9%. Merely giving a vanilla model the oracle files did not reproduce the gain. citeturn16view4

That study also contains the single most important safety result in this research. On **1,415 true OWASP vulnerabilities**, the strongest triage setup incorrectly dismissed **314**, retaining only **77.7%** of true positives: a **22.25% miss rate**. Weak crypto, weak hashing, trust-boundary violations and secure-cookie issues were particularly vulnerable to erroneous suppression. Therefore, the evidence argues strongly against a policy such as “agent says false positive → suppress from CI.” citeturn17view0

A safer in-house decision rule is therefore:

**scanner finding → agent gathers cross-file/config/runtime evidence → deterministic check where available → agent emits `confirmed | likely_false_positive | unresolved` plus evidence → human or explicit policy gate decides suppression.**

That arrangement captures the demonstrated FP-reduction benefit without giving the model the destructive capability that the true-positive-retention experiment shows it cannot safely hold. citeturn16view4turn17view0

The cost data reinforces using agents selectively rather than on every alert. In the study, Claude Sonnet 4 averaged about **13,321 tokens / US$0.0469** per Aider task, **219,299 / $0.1867** with OpenHands, and **130,846 / $0.1501** with SWE-agent. GPT-5/SWE-agent averaged 125,106 tokens and $0.1052 in the authors' pricing model. In other words, cross-file agentic investigation buys accuracy at a substantial token multiple, and there is no universally dominant framework. citeturn17view0

Cloudflare supplies complementary P3 field evidence for **agent proposes → fresh verifier challenges → executable proof where safe → human review**. Its fleet architecture separates hunters from validators and does not permit a validator to file its own original findings; fixes are checked with a target test intended to fail before and pass after the patch, while humans remain responsible for merge decisions. Cloudflare reports that independent validation materially improved the integrity of the production finding stream. citeturn4view4turn4view5

For **threat modelling specifically**, I found no dedicated open skill with a P1/P2 benchmark or a convincing P3 case history. Cloudflare's reconnaissance plus trust-boundary discipline is the best supported component, while Trail of Bits' context-building is a good prompt structure but remains P4 for efficacy. I would therefore **replace any elaborate in-house threat-model prose with a compact structured reconnaissance schema**, rather than adopt a third-party threat-model skill as authoritative. citeturn21search2turn20search4

For **authorization review**, use VulnGym's business-logic cases—explicitly including authorization bypass and broken authentication—as test material, and force the skill to represent `(principal, requested action, resource, policy/control, actual enforcement point, bypass path, security outcome)` rather than simply searching for middleware names. Cloudflare's rule that a confirmed finding needs an affected principal/resource/outcome is directly compatible with this. citeturn14search5turn21search2

### Reusable security evals

**VulnGym v0.1.5 is the highest-priority new benchmark for an in-house skill.** As of October 8, 2026 it contains **408 entries covering 184 advisories, all human-audited**, bound to real vulnerable project revisions with entry points, critical operations and cross-module traces. Its coverage deliberately includes business-logic flaws such as broken authentication and authorization bypass as well as conventional injection/path vulnerabilities. That makes it a much closer match to a repository-level security skill than snippet benchmarks. citeturn14search5

**CWE-Bench-Java** is especially useful for testing the scanner/agent composition. The original IRIS evaluation used 120 manually validated vulnerabilities; the current IRIS repository has expanded the dataset to **213 CVEs across 49 CWEs**, with vulnerable/fixed code and affected files/functions. Use a frozen version when comparing prompt revisions so dataset growth does not masquerade as skill improvement. citeturn17view1turn15search2

**OWASP Benchmark + Vul4J + post-cutoff OSS-Fuzz samples** are the best ready-made triage test design found. Critically, reproduce both halves of the 2026 study: measure FP dismissal **and true-positive retention**. Reporting only “noise reduced” would hide the exact failure seen in *Sifting the Noise*. citeturn15search1turn17view0

A cheap internal evaluation can therefore score at least: vulnerability/advisory recall; finding precision; FP reduction; true-positive retention after triage; correct principal/resource/authz reasoning; percentage with executable confirmation; percentage left honestly unresolved; and cost/tokens per confirmed finding. The evidence above suggests **TP retention should be a release-blocking metric for the skill itself**, not an afterthought. citeturn17view0

The key replacement I would make to a typical in-house codebase-audit skill is to **remove a large free-form “review architecture quality” prompt and replace it with several evidence collectors plus narrower judgement prompts**. This is an inference from the security evidence rather than a published codebase-audit result: both IRIS and the 2026 SAST study show that deterministic/cross-file evidence is more reliable than one-shot model judgement, and there is no contrary holistic-audit benchmark demonstrating that a broad monolithic prompt works. citeturn17view1turn16view4

### Reusable codebase-audit evals

I found **no published benchmark that adequately grades the full requested combination of architecture erosion + test health + quality + baseline drift for a coding-agent skill**. That absence should be recorded as a research result, not filled with a generic coding benchmark.

RepoAudit's benchmark can be reused only for the **repository reasoning / latent-bug** slice. Its published 15-project bug set can test whether the audit agent follows cross-file data flow and retains evidence, but it says nothing about architectural conformance or test health. citeturn6view0turn21search1

Trail of Bits' repository includes small skill eval fixtures. A useful example of its evaluation style is `review-walkthrough`: it constructs a throwaway seven-file repository with a seeded rate-limiter defect, grades mechanical criteria deterministically, and reserves the model judge for explanation quality. The maintainers explicitly warn that this small fixture “does not establish review quality across arbitrary repositories.” That is a good **eval-design technique**, not evidence that the codebase-audit problem is solved. citeturn20search12

For an in-house audit skill, a cheap benchmark should therefore create several medium-sized repository snapshots with known transformations: introduce a forbidden dependency edge; bypass one architecture boundary; remove tests from a critical path while keeping overall coverage superficially stable; make an ADR stale; create an API implementation/spec mismatch; add an unused alternate path; and seed one “looks bad but intentional” counterexample. Grade facts deterministically, then separately judge explanation/prioritisation. That benchmark would be substantially more decision-relevant than comparing the skill on SWE-bench-style implementation tasks.

OpenAI's skill and Kubernetes PRR solve complementary halves of the stage. The OpenAI skill is particularly strong on **release-candidate identity and software-contract change**, while Kubernetes is stronger on **production behaviour if the release is enabled and then fails**. A combined in-house skill should not force one prompt to rediscover both disciplines.

The strongest OpenAI mechanism is not its checklist; it is the **binding of approval to immutable candidate identity**. The release procedure says a generic approval, old-head approval or plain PR comment does not satisfy the gate; the human approval includes the full candidate SHA, and the readiness check is re-evaluated for that head. This directly addresses a common agent-pipeline failure: a review can be correct for revision A and silently become irrelevant after revision B. citeturn19search2

The strongest Kubernetes mechanism is its **production failure questionnaire**. The current template asks how the feature is enabled/disabled, what happens during rollout/upgrade/rollback, what should be monitored, whether resource exhaustion is possible, how it reacts when dependencies such as API server/etcd are unavailable, what other failure modes exist, and how operators troubleshoot SLO failure. Those questions map cleanly to services, desktop apps and backend systems even when Kubernetes itself is irrelevant. citeturn18search6

The resulting release artefact should be small and machine-consumable: candidate identity; change/compatibility summary; critical flows changed; required and observed checks; migrations; failure/rollback analysis; observability evidence; unresolved risks; security findings status; recommendation; and a **separate empty human-decision field**. That makes the handoff to a release gate explicit without giving the agent the capability to approve itself.

### Reusable release-readiness evals

There is **no mature public benchmark for release-readiness skills comparable with VulnGym** in the material found. The best public graded examples are field artefacts and process templates rather than labelled datasets.

OpenAI's **v0.23.1 release report** is a useful positive graded example because it records the exact base/target, release intent, compatibility judgement, scope and explicit human caveat, and it demonstrably travelled through the project's actual release process. It should be treated as an example of artefact quality, not evidence that the skill catches regressions better than alternatives. citeturn19search1turn19search2

Kubernetes' **KEP PRR questionnaire and historical reviewed KEPs** provide a much richer source for operational-readiness test cases. The questionnaire itself gives deterministic required fields across test plans, rollback, monitoring, dependency failure, scalability and troubleshooting, while the process requires independent PRR approval. citeturn18search6turn14search7

For a cheap in-house evaluation, freeze real historical releases and inject or select known release blockers: breaking API without version bump; migration absent; candidate changed after review; critical path lacks test; rollback is impossible; feature flag does not restore old behaviour; dependency outage causes unsafe state; monitoring does not observe the new failure; release notes omit a breaking change; secret-dependent integration test accidentally contacts production. Grade these facts deterministically. Then evaluate whether the skill finds the blocker, cites evidence, refrains from inventing evidence and leaves final approval to a human. That would test the properties the P3 systems actually rely on, instead of scoring prose similarity.

## Adoption architecture, risks, and decision

### Recommended stage composition

For **security analysis**, I would **adapt Cloudflare's skill structure**, not its complete prompt text. Keep a reconnaissance artefact, a coverage ledger, separate hunters and validators, the `confirmed / needs_validation / rejected` distinction, line/source evidence and the execution sandbox. Add an optional scanner-ingestion path using the independently evaluated SAST-triage pattern, but make “false positive” advisory rather than destructive. For stacks where deterministic semantic analysis is available, add the IRIS pattern: let the agent generate or broaden the analyser's specification, then let the analyser calculate the actual paths. citeturn21search2turn16view4turn17view1

That is a stronger design than either “LLM reviews code from scratch” or “run scanners and ask an LLM to suppress the noisy ones.” The 2026 evidence supports agentic cross-file investigation, but the 22.25% true-vulnerability suppression experiment is a clear warning that the agent must not own the suppression gate. citeturn17view0

For **whole-codebase auditing**, I would **replace rather than adopt**. None of the discovered holistic audit skills has evidence sufficient to justify its broad judgement rubric. Keep the useful architecture of “context model → deterministic measurements → narrow review passes → structured risk register”, then create the missing eval before trusting the stage. RepoAudit can inform cross-file memory/path traversal, but neither its scope nor its current licence permits treating it as the answer. citeturn6view0turn22view0

For **release readiness**, I would **adapt OpenAI's `final-release-review` mechanics and graft in Kubernetes PRR's operational questions**. This gives you exact-candidate identity, compatibility/release-diff reasoning, deterministic CI retention, rollback/failure/monitoring review and—most importantly—an explicit human approval transition. citeturn19search2turn18search6

### Risks uncovered in the third-party material

**Executable skill supply-chain risk is real even in reputable repositories.** The Trail of Bits issue tracker currently contains concrete examples: a static-analysis script silently dropping include globs, a `fp-check` hook blocking unrelated sessions, Claude-specific functionality causing portability problems, and a devcontainer workflow with two unpinned `curl | bash` installs. Another issue documents a composition failure where individually correct ASan/AFL++/libFuzzer skills produced a fuzzing setup that could terminate without meaningful fuzzing, potentially creating a false “no bugs found” impression. These are particularly relevant because an agent skill is executable operational guidance, not passive documentation. citeturn20search1turn20search9

**Treat every imported `SKILL.md`, hook, shell script and reference file as code that can instruct the host agent.** Before adoption, statically inspect allowed tools, shell commands, network destinations, credential access, writes outside the checkout, Git operations, package-install commands and hook behaviour. A skill's prose can function as privileged prompt instructions even where no conventional executable is present. The Trail of Bits failures above show why “well-known security vendor” is not an adequate sandbox boundary. citeturn20search1

**Cloudflare has the best explicit execution safety policy found.** Full audit output defaults outside the repository; target-controlled builds/tests/fuzzers require an OS-enforced sandbox, disabled external networking, an allowlisted environment, resource limits and scratch-only writes. Without those controls, the workflow is instructed to leave the candidate unconfirmed rather than execute it. That pattern is worth standardizing across *all* pipeline skills, not just security. citeturn21search2turn21search6

**VulnHunter is the clearest dual-use candidate.** It explicitly performs vulnerability discovery and exploitation, is optimized for Claude Opus, asks users to ensure they have authorization, and points first-party Anthropic users toward its Cyber Verification Program. Its headless modes can clone repositories, scan them and open GitHub issues, while its fixer requires authenticated GitHub tooling. Authorization is therefore primarily a policy/user responsibility rather than a strong local capability boundary. Any lifted technique should default to source-only or sandboxed local proof and require a fresh explicit decision before exploit execution or any network interaction with a live target. citeturn20search11turn21search7

**Repository-controlled instructions are another security boundary.** Audit agents necessarily read README files, comments, fixtures, test data and project-specific agent instructions. A secure pipeline should distinguish *evidence from the target* from *instructions to the auditor*. Cloudflare's parent/validator separation and sandboxing reduce consequences, but an in-house host should go further: target text should never be able to grant network access, secrets, extra filesystem permissions or permission to change the evaluation rubric. This is an architectural inference from the candidates' tool surfaces and the general nature of file-loaded skills, not an effectiveness claim from their authors. citeturn21search2turn20search4

**Licensing needs to be checked at the exact commit, not copied from search metadata.** RepoAudit is an instructive example: older indexed material still exposes an MIT licence, while the repository's current licence checked October 27, 2026 is a Purdue **non-commercial** licence restricting commercial use and derivative redistribution. For an in-house commercial delivery pipeline that makes the current implementation a non-candidate unless separately licensed. citeturn21search5turn22view0

**The broad `codebase-audit` skill has the opposite licence problem: no reusable licence was surfaced at all.** Regardless of its 83 stars, copying its detailed prompts into a company skill should wait for a clear licence or permission. It also performs live discovery and can file real remediation tickets, making its network/write permissions materially broader than a read-only audit needs. citeturn21search0turn21search8

**AWS's readable agent plugins expose a fit failure that is easy to overlook:** some analysis workflows explicitly mandate telemetry and rely on AWS services/MCP/CLI access. That is reasonable for their intended ecosystem but directly conflicts with the requested “no required hosted service, account or telemetry” criterion. citeturn19search8turn18search1

### Adopt, adapt, or replace

The evidence supports a fairly crisp portfolio decision.

| Stage/component | Decision | Proven parts to retain |
|---|---|---|
| Security audit orchestration | **Adapt Cloudflare `security-audit`** | Reconnaissance before hunting; explicit trust boundaries; coverage ledger; candidate states; fresh validator; schema validation; sandboxed proof; structured handoff; human review. **P3.** citeturn21search2turn4view5 |
| Scanner-output triage | **Build/adapt from the 2026 evaluated pattern** | Cross-file multi-turn investigation, config lookup and lightweight tool verification; **never automatic suppression**. **P2 independent evidence for existing agent frameworks.** citeturn16view4turn17view0 |
| Agent + static analyser vulnerability finding | **Lift IRIS architecture** | Agent supplies domain semantics/specifications; static analysis establishes paths; contextual review follows. **P1.** citeturn17view1turn17view2 |
| Threat modelling | **Replace current implementation with a smaller structured recon skill unless it already resembles Cloudflare** | Principals/assets/trust boundaries/entry points/assumptions/controls/open questions; no vulnerability verdict during mapping. **P3 via Cloudflare's broader workflow; no dedicated proven threat-model skill found.** citeturn21search2 |
| Authorization review | **Adapt the security workflow, not a separate unproven skill** | Principal-resource-action-control-bypass schema; test with VulnGym auth/authz examples. citeturn14search5 |

| Production/operational readiness | **Adapt Kubernetes PRR questionnaire** | Enable/disable, rollout, rollback, monitoring, dependencies, scalability, failure modes, troubleshooting, independent reviewer. **P3.** citeturn14search7turn18search6 |

The most important architectural consequence is that the pipeline should not have one generic “review agent.” The evidence favours **asymmetric stages with different authorities**: deterministic tools generate or verify facts; reconnaissance agents build context without verdicts; hunters propose; independent validators challenge; release reviewers recommend against an immutable candidate; and a human or deterministic policy gate owns acceptance. Cloudflare, IRIS, the 2026 SAST study, OpenAI's release process and Kubernetes PRR all converge on that separation despite being developed independently. citeturn21search2turn17view1turn16view4turn19search2turn14search7

That convergence is more compelling than any individual prompt pack. The evidence does **not** justify replacing human decision points with an agent; it does justify replacing several broad, free-form in-house prompts with narrower stages whose outputs can be checked, replayed and benchmarked.
