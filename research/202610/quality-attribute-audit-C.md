# Security and Performance Rubrics for Auditing an Existing, Mostly Agent-Written Codebase

## Executive answer: turn the profile into executable audit criteria

The right unit of analysis is not “does this repository follow security/performance best practices?” It is **“can this as-built system satisfy a concrete security or performance scenario implied by its operating profile?”** That matches established quality-attribute practice: SEI’s Quality Attribute Workshop method derives architecture-critical qualities from business and mission drivers and expresses them as scenarios; Microsoft likewise treats threat modelling as a way to identify security requirements, threats and mitigations and notes that it can be applied to an existing system, not only at initial design time. OWASP ASVS v5.0.0, current when checked on 2026-10-12, is then useful as a control catalogue; NIST SSDF v1.1, published February 2022, is useful for secure-development and supply-chain expectations, but neither should replace a system-specific threat model. citeturn7search0turn4search2turn20view0turn20view2

**Evidence labels used below:** **Established** means standards, mature platform guidance or long-standing engineering practice; **Emerging** means measured 2025–2026 research, especially on coding agents; **Recommendation** means my synthesis for this audit method. Vendor claims about a scanner's *effectiveness* are not treated as evidence; vendor/project documentation is used only to establish what a tool does and how it operates.

A useful deterministic pipeline is:

`profile facts → quality-attribute scenarios → invariants/budgets → mechanical candidate extraction → model judgement → measurement where required → fresh-context refutation`

For each scenario I recommend an adapted six-field record: **stimulus source, stimulus, operating environment, affected component/resource, required response, measurable response criterion**. For security, add the asset/trust boundary and attacker capability. For performance, add workload rate and cardinality. This is a practical adaptation of SEI quality-attribute scenario practice and STRIDE-style threat modelling. STRIDE supplies the threat prompts—spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege—but the audit should apply them to the **as-built data flows and trust crossings**, not mechanically label every component with all six categories. citeturn4search6turn7search0

Performance budgets should likewise come from the profile rather than generic “fast” thresholds. Web performance budgets can legitimately constrain transfer size, request count and user-visible timing, but web.dev's examples are examples rather than universal limits. For public web applications, Google's current Core Web Vitals provide one defensible external baseline: at the 75th percentile, “good” is LCP ≤ **2.5 s**, INP ≤ **200 ms**, and CLS ≤ **0.1**; Google says those thresholds were chosen by balancing user-experience quality with practical achievability, and the threshold methodology page was last updated 2025-05-07. These are web-user-experience thresholds, not backend, Electron or multiplayer capacity thresholds. citeturn6search0turn20view3

Capacity targets require more than “2,000 concurrent” or “100,000 concurrent.” They need a workload model: requests or messages per unit time, session behaviour, data cardinalities, bursts and representative mixes. Current Google Cloud capacity-planning guidance similarly starts from user/request rate, spikes, seasonality and growth, then tests capacity against performance and reliability objectives; its load-testing guidance treats the practical capacity point as the request rate at which tail latency remains within the SLO while resources remain in acceptable operating ranges. citeturn10search5turn10search9

**The ten performance checks that should dominate this audit**

| Priority check | Profile facts that make it apply | Audit question |
|---|---|---|
| **Request/RPC/query fan-out per screen or route** | High request rate, slow/expensive downstreams, mobile networks, many microservices | How many downstream operations can one user operation amplify into, including calls in loops and branches? |
| **N+1 database or RPC access** | List/detail pages, GraphQL/resolvers, ORM-heavy services, object-by-object remote lookup | Does work scale with result cardinality because remote/storage calls occur once per item rather than being joined, prefetched or batched? |
| **Unbounded lists, queries, payloads and missing pagination** | Large/growing datasets, untrusted clients, mobile clients, high concurrency | Is there a profile-derived upper bound before fetching, buffering, sorting, serializing or returning data? |
| **Blocking or synchronous work on latency-critical threads/loops** | Node event loop, browser/Electron renderer/main process, async Python service, UI thread, realtime tick loop | Can disk, network, crypto/compression, child-process or long CPU work prevent unrelated work from progressing? Electron explicitly recommends avoiding blocking main and renderer processes. citeturn18search0 |
| **Render cascades and excessive main-thread work** | Web/mobile browser or Electron UI, low-end devices, interaction latency is important | Which state/context/layout changes cause unnecessary commits or long tasks, and do they harm representative interactions? React's Profiler and Chrome Performance tools exist because source inspection alone cannot reliably quantify this. citeturn5search7turn5search6 |
| **Bundle/dependency/start-up weight** | Web over constrained networks, low-end mobile, Electron start-up, large JS dependency graph | What does the production artefact actually transfer/load/parse/execute, and which modules account for it? Webpack stats and esbuild metafiles expose the build graph; source dependency counts alone do not equal shipped bytes. citeturn14search0turn14search1 |
| **Memory and resource retention** | Low-memory mobile/desktop, long-lived processes, many connections/sessions | Do listeners, maps/caches, closures, buffers, timers, goroutines/tasks or per-session structures remain reachable after their logical lifetime? Chrome recommends heap/allocation tooling because retained objects are best confirmed at runtime. citeturn18search2 |
| **Polling, retry and reconnect amplification** | Many active clients, battery/network constraints, realtime systems, unstable networks | What request/message rate follows deterministically from timer periods, retry policies and client counts, and do synchronized reconnects create spikes? |
| **Caching and invalidation** | Repeated expensive reads/computation, remote services, DB-heavy routes | Is repeated work sufficiently reusable to justify caching; are TTL/size/invalidation semantics bounded and correct? “No cache” is normally a candidate until reuse and cost are measured. |
| **Hot-path algorithmic, serialization and batching cost** | Large N, realtime ticks, high throughput, large state objects | Do nested scans, repeated encoding/copying/sorting or tiny individually dispatched operations scale with profile cardinalities in a way that threatens the stated budget? |

The **minimum profile required before severity can be judged** is deliberately small but non-negotiable:

| Dimension | Minimum facts | What can still be done if missing |
|---|---|---|
| **Security** | Deployment/exposure; trust zones; principals and authentication model; tenant/ownership boundaries; sensitive-data classes; secrets/keys; privileged or monetary operations; platform/process capabilities; third-party/update path; important availability/safety stakes | Candidate extraction and scanner runs are still valid, but severity and sometimes applicability are not. A “missing authorization” candidate cannot be rated without knowing whether the object is private, tenant-scoped or intentionally public. |
| **Performance** | Representative flows; client/device class; network assumptions; active concurrency **and** request/message rate; peak/burst shape; important data cardinalities and payload sizes; SLO/user budget; deployment/resource shape; important DB/cache/downstream dependencies | Static amplification candidates can be extracted, but claims such as “too slow,” “won't scale” or “needs caching” are not findings until tied to a budget, deterministic bound or measurement. Google SRE practice likewise grounds performance in latency, traffic, errors and saturation rather than one generic utilization number. citeturn13search1turn13search2 |

The practical rule is therefore: **missing profile data lowers confidence, not standards**. Extract the evidence, state the unknown, and do not let a model invent the workload, data size, attacker capability or hardware.

A particularly important distinction is **“scanner detects a weakness pattern” versus “the audit proves the system's security property.”** A scanner can often identify a string-to-shell flow. It generally cannot infer that every access to `tenant_id=17` is authorized for the current caller, that an IPC bridge exposes too much application authority, or that an updater's trust root is appropriate to the stakes. OWASP's authorization guidance is explicitly business/context dependent, which is why the latter checks remain rubric judgements even when candidate extraction is mechanized. citeturn19search0turn19search4

**What the 2025–2026 evidence actually says about agent-written code**

The evidence is now strong enough to justify **extra scrutiny**, but not strong enough to assign a universal “AI code vulnerability rate.” The major studies use different languages, tasks, models and metrics, and several are research preprints. Their numbers should not be pooled.

| Measured study | Scope and measured result | What it supports for this audit | Scanner versus review implication |
|---|---|---|---|
| **BaxBench, 2025** | 392 backend-generation tasks spanning multiple languages/frameworks; the 11 models evaluated in that version did not exceed **37% correct-and-secure generation**. citeturn21view2 | **Emerging evidence:** passing functional behaviour does not imply secure implementation, even for relatively bounded backend-generation tasks. It is not direct evidence about mature repositories. | Dynamic/security tests can expose concrete weakness classes; semantic authorization and architecture/trust assumptions still require review. |
| **When Developer Aid Becomes Security Debt, 2025** | More than 12,000 coding-agent actions over 93 software setup tasks and five LLM backends; **21% of trajectories** contained at least one classified insecure action. The dominant classes were information exposure (CWE-200), improper access control (CWE-284) and downloading code without integrity checking (CWE-494). citeturn21view0turn21view1 | **Emerging evidence:** agents performing setup/tool work use security-relevant shortcuts, not only insecure application algorithms. This directly supports auditing CI/install scripts, permissions, secret exposure and downloaded tooling. | `curl … | sh`, permissive modes and obvious secret handling are mechanically detectable; whether a permission, credential exposure or disabled control violates the actual trust model needs judgement. |
| **SecRepoBench, 2025** | 318 secure-completion tasks in 27 real C/C++ repositories covering 15 CWEs. Its best reported agent setup, OpenHands + o3, reached **53.5% secure-pass@1**, while still failing to produce both correct and secure code on nearly half the tasks. citeturn15view0 | **Emerging evidence:** repository context helps agents relative to standalone completion in some settings, but does not remove the correctness/security gap. | Repository-aware security tests and SAST are useful candidate generators; passing ordinary tests is insufficient. |
| **How Safe Are AI-Generated Patches?, v3 December 2025** | Across 21,294 SWE-bench issues, the standalone Llama 3.3 patches had **135 manually confirmed newly introduced vulnerabilities** versus **12** in the corresponding developer patches after the authors' conservative multi-scanner filter; common LLM classes included command injection, `eval` injection, insecure deserialization and path traversal. Agentic workflows on the smaller 2,294-issue test set also introduced confirmed vulnerabilities. citeturn15view3turn15view2 | **Emerging evidence:** generated fixes can create new security debt unrelated to the bug being solved. The study also found vulnerability incidence associated with missing issue context, strengthening the case for inspecting agent-created “simple shortcuts” around ambiguous code. citeturn15view3 | The paper used Bandit, Semgrep and CodeQL plus majority filtering and manual validation. The authors also compare SAST before/after patches and report agent-introduced suspicious security changes. citeturn15view1turn21view3 | **Emerging evidence:** multi-file repository edits in realistic vulnerability contexts remain difficult even for 2026 agents, particularly where correctness and memory/security properties must both hold. | Memory-safety tests/fuzz-derived checks/SAST can catch many concrete C/C++ failures; choosing the right ownership, lifetime and trust semantics remains a reviewer task. |

The 2025 patch study also offers a useful caution about **autonomy and edit scope**: its OpenHands workflow produced far more confirmed security findings than two more constrained frameworks, and some problematic trajectories made very large, broad repository changes. The authors describe narrower edit scope as a plausible risk limiter, not a proven causal guarantee. That distinction matters: this supports an audit check for **unexpectedly broad agent-written subsystems and reimplementations**, but not a rule that “large agent diffs are vulnerable.” citeturn15view3

The agent-specific defence set that follows from the measured evidence is therefore narrow and concrete: scan the **whole as-built repository**, not merely the final diff; scan Git history for secrets; enumerate permissive permissions and downloaded/executed code; give extra manual attention to authorization and trust-boundary decisions; inspect suspiciously broad replacement implementations; and never let passing functional tests discharge a security finding. The fresh-context verifier in your existing audit is particularly well suited here: for every serious finding it should attempt to construct an alternative interpretation under which the code is secure and should downgrade the finding when that interpretation survives. This is a **recommendation**, supported by the repeated correctness/security gap across the 2025–2026 benchmark evidence above. citeturn21view2turn15view0turn15view1

## Performance rubric, measurement boundary and platform differences

Static performance review works best when it looks for **amplifiers and missing bounds**, not guesses about milliseconds. A route making five unconditional downstream calls genuinely has five static call sites; a polling interval really can be extracted from configuration; a query nested inside a loop really has cardinality-sensitive behaviour. What cannot be inferred safely is how expensive those operations are on real hardware, how often branches are taken, what cache hit rate occurs, or where CPU time actually lands. Electron's own performance guidance makes the same distinction in plainer terms: measure/profiling is the reliable way to locate the resource-hungry code after obvious structural problems have been identified. citeturn18search0

A useful report state is therefore **Finding / Candidate / Not applicable**. A static performance candidate should still contain an anchor, code-derived amplification or lifecycle mechanism, the relevant profile fact, and the exact measurement that would confirm/refute it. For the user's specific **2,000 versus 100,000 concurrent** comparison, there is no industry threshold at which a new architecture rule suddenly becomes mandatory. But identical per-client behaviour is **50× larger at 100,000 than at 2,000**: a 1-unit per-connection allocation, polling schedule, heartbeat, broadcast recipient scan or reconnect action multiplies by 50. That is derived arithmetic, not a benchmark. At 100,000, the rubric should therefore elevate per-client memory, polling, broadcast amplification, connection limits, backpressure, reconnect storms and capacity evidence from “check when relevant” to routine checks. At 2,000, those checks can still be severe when the service has tight realtime latency, expensive messages or small hardware; concurrency is not a substitute for workload rate or stakes. Capacity planning should remain SLO- and workload-driven at either scale. citeturn10search5turn10search9

## Deterministic tooling by stack

The safest default runner is a **pre-staged audit toolchain**, not `npm install`, `pip install`, `go install` or Maven/Gradle modification inside the target repository. Pin each scanner/runtime by exact release and preferably artifact hash or container digest; place it outside the repository; mount or expose the repository read-only; write databases/results to a separate scratch directory; and disable network. If a measurement necessarily executes the audited application or production build, move to an isolated worktree/container/VM, keep egress blocked unless the test explicitly requires an approved external dependency, and record the exact command, tool/runtime version and input profile. This is a **recommended operational policy**, not a claim that every tool is inherently sandbox-safe.

Two current tool behaviours are especially helpful for that policy. OSV-Scanner's documented `--offline` mode uses a previously downloaded local vulnerability database and says it neither updates it nor sends project/dependency information anywhere. Semgrep can run local rules with metrics disabled; avoid features that invoke local dependency builds in a strict untrusted-repository audit. CodeQL supports no-build extraction for several languages, but where extraction requires a build, treat that build as audited-code execution rather than “just scanning.” citeturn17search5turn11search1turn11search9turn11search0

For tools packaged as OCI images, the general pattern should be conceptually:

```text
pre-pull IMAGE@sha256:<approved-digest>

run:
  network = none
  repository = read-only
  output/tmp = separate writable volume
  tool configuration/rules/database = read-only, pre-staged
```

Do **not** use a floating `latest` tag or permit the tool to silently install project dependencies during the audit.

There is **no stack-independent static tool that can reliably prove N+1 behaviour, missing caching, incorrect authorization placement, or “too many requests.”** Those properties depend on framework behaviour and profile semantics. The deterministic substitute should be a small family of audit-owned extractors that output facts, not verdicts:

`entry-point → auth middleware → authorization enforcement point → DB/RPC/process/filesystem sinks`

`screen/route → downstream call sites → enclosing loop cardinalities → configured retries/polls`

`cache → key fields → max entries/bytes → TTL → mutation/invalidation sites`

`ingestion point → parser → pre-parse size bound → post-parse type/count/depth validation`

`runtime trace request-id → normalized SQL/RPC template → call count → total observed duration`

The model then judges those facts against the profile. That division is particularly important for agent-written repositories because it prevents the reviewer model from “seeing” a loop and inventing an N of 10,000, or seeing a cache and inventing a hit rate.

Scanner configuration itself should be extracted just as mechanically as source code. Produce a machine-readable manifest containing scanner name/version/hash, ruleset/query-pack version, included/excluded files, supported language coverage, lockfiles/SBOMs scanned, Git-history coverage, network mode and whether the tool executed any project code. That manifest is an audit artefact and a direct defence against the false confidence created by a green but incomplete scan.

## Severity calibration and scaling from a local tool to a 100,000-user service

For security, the most useful published schemes are **CVSS v4.0** and **SSVC**, but neither should be copied wholesale as the audit's single severity score.

CVSS v4.0, released 2023-11-01, separates **Base, Threat, Environmental and Supplemental** metrics; its Environmental group is explicitly designed to represent characteristics unique to the user's environment. That makes CVSS appropriate for describing a concrete vulnerability, particularly a known dependency CVE, but less natural for findings such as “authorization enforcement is distributed and bypassable,” “secret scanner excludes history,” or “Electron renderer exposes an over-broad bridge.” citeturn20view4

CISA's implementation of **SSVC** takes a decision-oriented approach rather than treating a CVSS number as the whole prioritization answer, incorporating factors such as exploitation and impact into remediation decisions. OWASP's risk-rating guidance similarly frames risk as likelihood × impact and says the model should be customized to the organization. These are better precedents for a profile-sensitive codebase audit. citeturn12search1turn12search2

**Recommendation:** keep severity categorical and derive it from explicit profile facts rather than a home-grown decimal score.

| Level | Security interpretation | Performance interpretation |
|---|---|---|
| **Critical** | Credible low-precondition path to catastrophic profile impact: broad cross-tenant compromise, remote privileged code execution, signing/admin credential compromise, irreversible large-scale money/safety impact. | Measured or deterministically proven inability to operate at the **normal required profile**, with catastrophic availability/safety/money effect and no graceful fallback. Rare for ordinary UI performance. |
| **High** | Credible path to major confidentiality/integrity/availability impact on an important asset, or broad tenant/user blast radius, even if authentication or another realistic precondition is needed. | Measured breach of a dominant flow's SLO/capacity budget at required peak, or deterministic amplification/resource exhaustion under the declared workload. |
| **Medium** | Real weakness with constrained blast radius, meaningful preconditions or defence-in-depth significance, but no demonstrated catastrophic path. | Measured secondary-flow regression or a strong static candidate whose amplification and profile make a budget breach plausible but unconfirmed. |
| **Low** | Hygiene/hardening gap without a credible current exploit path under the profile. | Bounded/cold inefficiency with little expected user/capacity effect, or a speculative optimisation opportunity. |
| **Candidate / unverified** | Evidence exists but missing trust/data/exposure fact prevents severity. | Static risk exists but latency, CPU, memory, hit-rate or capacity effect still requires measurement. |

A useful security severity record should therefore contain the five inputs **exposure, attacker/precondition, asset, blast radius, impact**. Confidence is separate: a scanner alert can be “High impact if real, low confidence,” rather than having its severity artificially reduced because the scanner is noisy.

Performance should be stricter: **an unmeasured static candidate should normally not receive a final High or Critical performance severity** unless the violation follows deterministically from the source/configuration plus profile values. For example, if a profile states 100,000 simultaneously active clients and source/config says every active client emits one request every fixed interval, a script can calculate the resulting configured request rate exactly. That can support a real finding if it exceeds a documented external quota or capacity budget. By contrast, the same script cannot infer that a function takes 14 ms.

The profile can radically change the same source-level evidence:

| Same code evidence | Local/lockstep desktop tool | Public multi-tenant service |
|---|---|---|
| **Object lookup by caller-supplied ID with no visible ownership check** | Often N/A if there is exactly one local principal and no privilege boundary; reassess if opening arbitrary untrusted project files has authority consequences. | Potentially High/Critical if IDs cross tenant/user boundaries. OWASP treats object-level authorization as a per-request responsibility. citeturn19search0 |
| **Hard-coded token** | Low if demonstrably fake/local; High if the desktop binary distributes a shared production service credential to every installation. | High/Critical if it grants production DB/cloud/signing/admin authority. Secret scope and rotatability drive impact. citeturn19search2 |
| **Electron renderer can invoke broad filesystem/process IPC** | Still serious if the renderer loads any untrusted content/document, because compromise crosses into native privilege. | N/A to a non-Electron backend, but an equivalent server plug-in/process boundary should be assessed instead. Electron specifically recommends narrow context-isolated IPC APIs and sender validation. citeturn8search0turn8search4 |
| **Synchronous disk read on request/interaction path** | Low if one-off startup on a workstation and outside an interaction budget; potentially user-visible if repeated on main process. | Potentially High after measurement on a single event loop at high request concurrency. Electron/Node guidance emphasizes avoiding blocking critical processes, but actual severity remains workload-dependent. citeturn18search0 |
| **Per-client polling** | One desktop instance may make the traffic negligible. | At 100,000 active clients, identical per-client traffic is 50× the aggregate of 2,000 clients. Actual downstream impact remains a measured capacity question. |
| **Per-connection retained allocation** | One/few connections may be irrelevant. | At unchanged bytes/connection, 100,000 clients consume 50× the aggregate connection-state memory of 2,000. The bytes/connection should come from profiling, not a model. |
| **Unbounded “load all records” list** | Low if records are physically bounded by a tiny local format. | High candidate when a multi-tenant production table grows continuously or the caller can influence cardinality. |
| **No overload/backpressure mechanism** | Usually irrelevant for an offline single-user operation. | Increasingly important for large public or realtime workloads; Google SRE guidance says a serving system should accept only the work it can process and reject/degrade excess load predictably. citeturn18search1 |

Security severity should **not** automatically rise from 2,000 to 100,000 concurrency: a broken tenant check is severe because of exposure, asset and blast radius, not because the server has more sockets. Concurrency principally magnifies denial-of-service/resource-exhaustion impact. Conversely, a two-user payment/signing system can have Critical integrity findings despite negligible load.

For capacity, do not create a generic rule such as “CPU must remain below 70%” or “100k concurrent requires microservices.” There is no defensible universal threshold. The audit should instead require the profile's own SLO and workload, then identify the **capacity inflection point** from a short isolated measurement if capacity is a serious concern. Google and AWS current guidance both frame capacity in terms of latency/error/throughput behaviour plus resource saturation rather than a single universal utilization cutoff. citeturn10search9turn10search2

For web clients, the one exception where externally standardized numeric thresholds are genuinely useful is Core Web Vitals. Use Google's p75 LCP/INP/CLS thresholds as a baseline where the product has not chosen stricter objectives, explicitly labeling their source and date; do not turn Lighthouse's many diagnostic thresholds or example performance budgets into product requirements unless the profile adopts them. citeturn20view3turn6search0

The most defensible final finding schema for both dimensions is therefore:

```text
criterion
status: finding | candidate | N/A
profile facts that activate it
anchor: path:line | scanner record | build artefact | measurement
mechanism / concrete failure path
mechanically computed quantities
measurement evidence, if required
affected asset / user flow
severity
confidence
known assumptions
refutation attempted by verifier
recommended smallest sufficient remediation
```

That shape forces the distinction the research repeatedly supports: **facts are extracted or measured; meaning is judged; serious claims are then challenged.**

## Reliability, accessibility and observability verdict

These attributes should not all be folded into security/performance.

| Attribute | Recommendation | Why |
|---|---|---|
| **Reliability / resilience** | **Make it a separate conditional audit dimension** for public services, realtime/multiplayer, stateful systems and any profile where availability/data integrity/recovery are dominant quality attributes. For a small offline desktop utility, folding the few relevant checks into architecture may be enough. | Reliability has failure modes that neither security nor performance captures cleanly: retries and retry safety, idempotency, timeout propagation, overload/cascading failure, graceful degradation, recovery, state integrity and dependency failure. Google SRE treats SLOs, monitoring, testing, capacity planning, overload handling and cascading-failure controls as distinct reliability disciplines. citeturn13search2turn13search4turn18search1 |
| **Accessibility** | **Make it a separate conditional dimension for user-facing web/mobile/desktop software.** Do not fold it into performance. Mark it N/A for headless services except where they produce user-facing content/interfaces. | WCAG 2.2 is a W3C Recommendation with independently testable success criteria, and W3C recommends using the current version. WCAG 2.2 adds criteria beyond 2.1; accessibility failures such as keyboard traps, missing accessible names or insufficient target/focus behaviour are not meaningfully security or performance findings. citeturn13search0turn13search3 |
| **Observability** | **Usually fold into reliability/operability, with security-relevant audit logging remaining in security.** Promote observability to a standalone dimension only when operational diagnosability is itself one of the profile's dominant attributes. | SRE's “golden signals”—latency, traffic, errors and saturation—show that telemetry is foundational to proving service health and performance, while security logging serves a distinct investigative/control function. Treating every missing metric as a standalone quality failure risks auditing instrumentation rather than outcomes; treating a system with no way to observe its SLOs as fully verifiable is equally weak. citeturn13search1turn19search1 |

The strongest case for adding a third dimension is therefore **reliability/resilience**, particularly for the same profiles that make performance important at scale. Performance asks *“can it meet the required response/capacity under the intended workload?”* Reliability asks *“what happens when dependencies, machines, networks, clients and the system itself fail or exceed assumptions, and can it recover without corrupting state or causing a cascade?”* Those questions overlap at overload but are not interchangeable. citeturn18search1turn13search4

Accessibility is even more clearly independent for user-facing systems: WCAG gives it an established normative, testable basis rather than forcing accessibility failures into unrelated architecture or performance categories. citeturn13search0

Observability is different. It is often an **enabling quality** for the other two: without route-level latency/error/saturation data, a high-scale service's performance and reliability claims may simply be unverifiable. The audit should therefore be able to issue a reliability/operability finding such as “the stated p99 SLO cannot be evaluated because the service records no latency distribution by route,” while retaining sensitive-event logging, authorization failures and secret-safe logging under security. That division is consistent with SRE monitoring practice and OWASP's security-logging guidance. citeturn13search1turn19search1

The overall recommendation is consequently:

**Security** should be a profile-driven, threat-modelled rubric whose mechanical layer inventories boundaries, authorization coverage, ingestion, dangerous sinks, secrets, dependencies, sandbox configuration, logging and scanner coverage. The model's job is chiefly to connect those facts into plausible security failure paths, not to rediscover them.

**Performance** should be an amplification-and-bounds rubric first and a profiler second. Static review can confidently expose fan-out structures, loops around remote operations, unbounded collections, sync APIs, polling schedules and unbounded caches; actual latency, capacity, rerender cost, leak magnitude, cache value and CPU dominance belong behind a measurement gate. Electron, Chrome, React, Python, Java and Go platform documentation all reinforce the value of profiling the actual runtime rather than inferring bottlenecks from appearance. citeturn18search0turn5search7turn16search0turn16search1turn16search2

And for **agent-written code**, the 2025–2026 evidence supports one important policy change rather than an entirely different security rubric: assume that functional success and plausible-looking implementation are weaker evidence of security than they would be in a heavily reviewed human codebase. The measured studies repeatedly find correct-but-insecure or insecure agent outputs, including unsafe setup actions, injection/deserialization/path weaknesses and difficult multi-file secure edits. The appropriate response is not an “AI penalty” in severity; it is stronger deterministic extraction, whole-repository scanning, particular scrutiny of authorization/trust/supply-chain shortcuts, constrained execution of audit tooling, and the fresh-context verifier you already intend to use. citeturn21view0turn15view3turn15view0turn15view1
