# Judging contract design in an existing codebase

## The ten checks that matter most

A useful definition for audit purposes is: **a contract-design defect exists when the surface a caller sees permits, promises, hides, or couples something materially different from what the implementation and surrounding system actually support**. The strongest findings are therefore contradictions, not stylistic preferences. An audit should normally anchor the finding on the declaration, schema, export, prop type, boundary parser, or error translation line, then cite implementation/call-site evidence showing why that declared contract is misleading.

I use three evidence labels below:

- **Established practice** — language specifications/documentation, standards, long-standing engineering guidance, or mature API-design literature.
- **Emerging evidence** — primarily 2025–2026 empirical work on coding agents; findings should not yet be treated as universal.
- **Audit opinion** — a proposed threshold or severity rule intended to make codebase audits consistent. It is deliberately distinguished from an industry standard.

The ten highest-value checks are:

1. **Required really means required, and optional really means supported absence.** Do not accept `?`, `Optional`, nullable types, defaults, or sentinel values merely because they save the author from fixing callers. Python explicitly distinguishes a nullable `Optional[T]` from an argument that is optional because it has a default; TypeScript's stricter optional-property/null settings similarly make distinctions between absence, `undefined`, and `null` visible. **Established practice, current 2026.** citeturn3search0turn2search0

2. **Failure is visible in the contract whenever callers need to distinguish it from success.** Empty collections, zero values, `null`, `false`, or cached/default data must not silently stand for I/O failure, parse failure, authorization failure, or a violated precondition unless that fallback is an explicit part of the API's semantics. Rust's `Result`, Go's error values, Python's exception hierarchy, and standardized RPC/HTTP error models are different language mechanisms for the same underlying requirement: callers need an honest failure channel. **Established practice, 2015–2026.** citeturn20search1turn20search2turn3search2turn8search0

3. **Types should rule out important invalid states rather than merely describe bags of fields.** A finite lifecycle represented by a discriminated union or state enum with state-specific data is usually stronger than `"status": string` plus many nullable fields. TypeScript's discriminated unions and `never` exhaustiveness checking are a concrete example. **Established practice, current 2026.** citeturn2search5

4. **Parse once at every trust boundary, then let trusted inner code consume the parsed type.** HTTP bodies, URL state, external API replies, messages, IPC data, persisted records, configuration and user input should normally become a stronger representation before entering business logic. Alexis King's 2019 “Parse, don't validate” formulation is especially useful here: parsing should preserve the fact that verification has happened instead of throwing that knowledge away and requiring repeated defensive checks. **Established practice, 2019.** citeturn5search0turn5search5

5. **Compiler escape hatches are contract debt, especially at boundaries.** Unchecked casts, `any`, non-null assertions and equivalent suppressions can be legitimate locally, but a cast immediately after deserialization is not parsing. This check deserves extra weight for agent-written TypeScript: a 2026 MSR study found agentic PRs in its dataset introduced `any` about nine times as often as human PRs and also used type assertions and non-null assertions more often. **Established principle; emerging agent evidence, 2026.** citeturn15view0

6. **The public surface should be intentional and measurable.** Wildcard re-exports, barrel files that expose helpers accidentally, public symbols that only exist for tests, and dependency/SDK types leaking through otherwise owned interfaces all expand the compatibility obligation. Hyrum's Law is a useful warning that observable behaviour tends to acquire consumers whether or not it was intended as API; tools such as API Extractor can mechanically snapshot and diff exported surfaces. **Established practice, current guidance/tools as of 2026.** citeturn7search0turn14search0turn14search6

7. **Errors should form one coherent taxonomy as they cross layers.** Database-, framework- and SDK-specific failures should normally be translated into errors meaningful to the next caller; the taxonomy should tell callers what they can do — fix input, treat as absence, resolve a conflict, retry, or report an internal failure — rather than expose every implementation-specific cause. Google AIP-193 and gRPC's canonical statuses exemplify this approach. **Established practice, 2019–2026.** citeturn8search0turn8search1turn8search8

8. **Schema evolution must be checked from the old consumer's point of view, not merely against today's producer.** Renaming/removing fields, changing presence semantics, reusing identifiers, narrowing accepted input, and changing observable output can be contract breaks. Protobuf's rules against reusing field numbers or adding required fields, Google's backward-compatibility guidance, and schema-diff tooling such as Buf illustrate the discipline. **Established practice, current 2026.** citeturn6search0turn1search2turn6search2

9. **Front-end contracts should expose one source of truth and real UI states.** Required props should be genuinely required; mutually exclusive variants should not be an unconstrained pile of booleans and optional fields; controlled components should not also maintain an independent competing state; URL/server payloads should be parsed before becoming application state. React explicitly treats props as the normal explicit data-flow mechanism, warns against overusing context, and describes the controlled/uncontrolled trade-off in terms of where the source of truth lives. **Established framework guidance, current 2026.** citeturn4search4turn4search5turn4search6

10. **Make contract regression harder than contract preservation.** Strict type checking, lint/AST checks for escape hatches and swallowed errors, public-API snapshots, schema compatibility checks, migrations in version control and contract tests are substantially more reliable than asking reviewers — human or agent — to remember every contract convention. Controlled 2026 evidence also suggests coding agents benefit materially from detailed static-type feedback. **Established tooling practice plus emerging agent evidence, 2026.** citeturn14search6turn6search2turn6search3turn16view6

For audit severity, the following is **audit opinion**, not a published standard: treat a contradiction as **Critical** when it can silently report success while causing corruption/data loss or incompatible persisted/wire state; **High** when invalid states or failures can routinely cross a boundary, or when a public compatibility break has real consumers; **Medium** for contained semantic ambiguity or inconsistent conventions that make misuse likely; and **Low** for excess surface/readability debt where behaviour remains unambiguous.

## Core rubric for signatures, errors, types, validation, and public APIs

The most useful rubric is intentionally asymmetric: it treats **contract widening** — accepting `null`, exporting more, returning vague types, suppressing type information — as suspicious only when that widening creates a state the implementation does not genuinely support. “More precise” is not automatically “better”; precision that forces every transient implementation detail into a type can be over-design.

| **Required versus optional** | `foo(x?: T)` or `x: T \| undefined`, but the first operation throws, asserts, or dereferences when `x` is absent; a constructor allows omission although no valid object can exist without the value. Judgment decides whether absence is actually supported, particularly for public/library APIs with unknown callers. | **High** if invalid objects cross layers; **Medium** for internal signatures whose only effect is caller confusion. | Do not make parameters required merely because all *current* callers happen to pass them if omission is intentionally supported API behaviour. |
| **Nullability and absence semantics** | The contract collapses distinct states such as “omitted”, “explicitly cleared”, “not loaded” and “not found” into one `null`; conversely, a nullable declaration is immediately converted into a non-null assertion. TypeScript's strict null and exact optional-property modes expose some of these distinctions. **Established, current 2026.** citeturn2search0 | Strong mechanical support from strict type checkers; semantic distinctions still require judgment. | **High** when absence controls persistence or API updates; otherwise **Medium**. | Separate types for `null` and omission are unnecessary where the application genuinely assigns them identical semantics. |

| **Overloads** | Overloads with the same name perform conceptually different operations, reorder equivalent arguments, or attach different semantics to similar types in the same position. Microsoft recommends overloads represent the same semantic operation and use consistent parameter ordering/naming. **Established .NET-specific guidance, 2008/2023.** citeturn9search1 | Compiler detects ambiguity; AST can compare sets/order. | **Name versus behaviour** | `getFoo()` writes state; `isValid()` throws on normal invalid input; `parse()` merely checks and returns the original unrefined value; `delete()` archives; `find()` creates on miss without the name/documentation indicating that. Explicit interfaces should capture caller assumptions rather than forcing callers to know hidden implementation conventions. **Established principle.** citeturn7search2 | Naming heuristics can generate candidates but false positives are high. Requires implementation/call-site judgment. | **Medium** normally; **High** when hidden side effects are destructive or externally visible. | Domain terminology may intentionally differ from generic CRUD vocabulary; audit the established local meaning before flagging. |
| **Return type exposes failure honestly** | A function that can fail for operational reasons returns the same `null`, `[]`, `0` or `false` used for a valid result; a declared non-null result is manufactured with a fallback after failure. Rust makes recoverable failure explicit via `Result<T,E>`; Go treats errors as ordinary values that must still be checked. **Established, 2015–2026.** citeturn20search1turn20search2 | Broad catches returning sentinels are mechanically searchable. Deciding whether the sentinel means legitimate absence or hidden error is judgment. | **High**, and **Critical** where the caller proceeds as though a write/transaction succeeded. | `findById(): T?` can be perfectly honest when “not present” is a normal outcome and infrastructure failures remain distinct. |
| **One error model per semantic class** | The same “not found” condition returns `null` in one repository method, throws in another and returns `{success:false}` in a third with no deliberate reason; equivalent endpoints map the same domain failure to different status codes. Standard taxonomies exist precisely so shared handling is possible. **Established, 2019–2026.** citeturn8search0turn8search1 | Searchable through return/throw/catch patterns and boundary mappings; proving semantic equivalence requires judgment. | **High** if callers make retry/transaction decisions from it; otherwise **Medium**. | Different layers do not need identical *representations*: a domain result may legitimately become an HTTP status or exception. Consistency means semantic correspondence, not identical syntax. |
| **Boundary error translation** | `SqlException`, AWS/Stripe/vendor SDK exceptions, ORM-specific codes or raw gRPC errors leak through an application-owned interface; or translation discards actionable distinctions such as conflict versus unavailable. Go's error-wrapping guidance explicitly notes that wrapping a lower-level error can make that error's identity part of your API. **Established, 2019.** citeturn2search7 | Imports/types in exported signatures are mechanically detectable. Mapping quality requires judgment. | **High** for long-lived/public contracts; **Medium** for internal seams. | A tiny adapter used only by code already coupled to the vendor gains little from inventing an elaborate domain hierarchy. |
| **Catch-and-default / swallowed errors** | `catch { return [] }`, `except Exception: return None`, an empty `catch`, a promise `.catch(() => defaultValue)`, or logging-and-continuing after a failure that invalidates subsequent work. | Very mechanically searchable; whether the fallback is contractually legitimate is judgment. | **High** by default when valid-looking success is returned; **Critical** around writes or corruption risks; **Low** for explicitly best-effort side effects. | Fallbacks are legitimate when degraded behaviour is an explicit product requirement — for example, optional recommendations disappear when their service fails — and the caller does not need to distinguish it. |
| **Invariant-bearing types** | Repeated checks such as `if id.startsWith(...)`, bounds checks, or normalization occur throughout inner code; interchangeable primitives represent non-interchangeable concepts such as `UserId` and `OrderId`; callers can construct values the implementation immediately rejects. “Parse, don't validate” advocates returning a representation that records what was proven. **Established, 2019.** citeturn5search0 | Repeated-guard and primitive-parameter analysis can suggest candidates. Whether the distinction merits a type is judgment. | **High** where confusion can mutate the wrong entity or violate persisted state; otherwise **Medium**. | A wrapper type for every incidental string/int makes APIs harder to work with. Encode stable, repeatedly relied-on distinctions, not every local predicate. |
| **State represented as states, not optional-field combinations** | `{status: string, data?: T, error?: Error, startedAt?: ...}` permits `status="success"` with `error` and without `data`; multiple booleans such as `loading`, `loaded`, `failed` allow contradictory combinations. Discriminated unions can associate each variant with exactly its valid fields and support exhaustive checking. **Established TypeScript example, current 2026.** citeturn2search5 | AST can identify clusters of status strings/booleans plus optional fields; proving illegal combinations matter requires judgment. | **High** when invalid state influences persistence/workflow; **Medium** for UI state. | Dynamic workflows with dozens of rapidly changing business rules may be clearer with runtime rules than an enormous type-level state machine. |
| **Boundary parsing** | Raw JSON/dictionaries/SDK objects move directly from HTTP, queue, storage or IPC into inner services; a type assertion follows deserialization; validation returns `bool` but code continues using the original unrefined object. Serde's deserialization model is a concrete example of turning serialized input into typed values while reporting mismatches. **Established, current 2026.** citeturn5search5turn5search0 | Boundary APIs and casts are highly searchable. Determining the proper parser location requires judgment. | **High** because untrusted/unversioned shape propagates inward. | Purely internal typed function calls do not need to repeatedly re-parse objects whose construction is already controlled. |
| **No shotgun validation** | Handler checks `x`; service checks the same `x`; repository checks it again; leaf helper checks it again, each with subtly different conditions. King's essay calls the general anti-pattern “shotgun parsing”: knowledge gained from checking is not represented in the resulting value. **Established, 2019.** citeturn5search0 | Duplicate-condition search can identify candidates; ownership of the invariant is judgment. | Usually **Medium** because drift creates contradictory behaviour; can become **High** where layers disagree. | A public library method may still validate independently because it cannot assume all callers entered through your normal outer boundary. |
| **Small, intentional public module surface** | Internal helpers/constants become exported; barrel files use broad `export *`; public classes expose convenience members with no supported use case; test helpers live in the production API. Hyrum's Law warns that observable behaviour can become depended upon; API Extractor explicitly targets accidental exports and API-surface diffs. **Established practice/tools, current 2026.** citeturn7search0turn14search0turn14search6 | Export counts, visibility and public-API diffs are mechanical. Determining intended support is judgment. | **High** for externally consumed libraries; **Medium** in a monorepo; **Low** for truly private applications. | There is no defensible universal maximum export count. A large domain can legitimately have a large facade; “small” means no unsupported surface. |
| **Owned versus vendor types** | An application-domain method accepts or returns the vendor client's request/response object, so upgrading the dependency changes callers; persistence models double as HTTP responses; framework request objects flow deep into application code. | Export-signature/import graph analysis is mechanical. Whether an adapter buys enough decoupling is judgment. | **High** across a durable package/service boundary; **Medium–Low** within a framework-specific leaf. | Wrapping every library type creates pointless DTO translation in code that is intentionally and permanently tied to that library. |

**How to choose the failure mechanism.** There is no language-agnostic rule that “exceptions are bad” or “all failures should be `Result`.” The better decision variable is **what the caller is expected to do**. A normal absence can be an `Option`/nullable return. A recoverable expected outcome that callers routinely branch on fits a result/either style particularly well; Rust makes this distinction explicit with `Result<T,E>`. Languages with exception-centric APIs can reasonably use typed exceptions when most intermediate callers merely propagate them. At a process or wire boundary, failures normally need serializable stable statuses/codes plus machine-readable details, as in gRPC status codes and RFC 9457 Problem Details. Programming invariant violations should not be disguised as routine business alternatives. **Established practice, 2015–2026.** citeturn20search1turn3search2turn8search1turn8search2

A coherent **error taxonomy is semantic, not implementation-shaped**. “Postgres unique violation”, “Axios 503”, and “SDK timeout” are causes; “conflict”, “unavailable/retryable”, or “internal failure” are usually more stable contracts for the next layer. Google's AIP-193 standardizes error representation in part so common errors can receive common handling, while AIP-194 ties retry behaviour to the meaning of the status — for example distinguishing invalid input from transient unavailability. **Established practice, 2019.** citeturn8search0turn8search8

That leads to a useful audit test: **would replacing the database, HTTP client, cloud SDK or serialization library force unrelated callers to change their error-handling branches?** When the answer is yes, an implementation error has probably leaked through a longer-lived contract. The caveat is important: Go's wrapping guidance notes that exposing wrapped error identity can intentionally become part of the API, so the defect is not “lower-level errors exist”; it is exposing them accidentally. **Established Go-specific guidance, 2019.** citeturn2search7

**When to encode an invariant in a type.** My recommended audit threshold is to do so when several of these are true: the rule is repeated at many call sites; invalidity has a meaningful cost; the semantic distinction is stable; values enter through a small number of construction/parsing points; or the state space is finite enough that exhaustive checking buys something. IDs from different namespaces, validated external identifiers, non-empty/normalized domain values, money/currency pairs and lifecycle variants often qualify. Local formatting predicates and fast-changing policy rules often do not. This is an **audit opinion** informed by parse-don't-validate and discriminated-union practice rather than a universal type-theory rule. citeturn5search0turn2search5

**Where the trust boundary is.** HTTP and user input are obvious, but an audit should also treat **external API responses, message queues/events, IPC, files/configuration and storage deserialization** as parsing boundaries. Persisted data deserves particular attention because it may have been written by an older application version, an out-of-band migration or another tool; a static language's current in-memory type does not retroactively guarantee an old row/document has that shape. The target pattern is therefore:

> untrusted or versioned representation → parse/deserialize once → invariant-bearing internal value → trusted inner functions

rather than:

> raw payload → cast → service → defensive check → repository → slightly different defensive check.

The first pattern follows the information-preserving rationale of parse-don't-validate; the exact list of what a particular application treats as “untrusted” is **audit judgment**. citeturn5search0turn5search5

Finally, **public-surface size should be measured but not optimized to a magic number**. Useful mechanical metrics are exported symbol count, newly exported symbols per release, wildcard re-export count, transitive exported dependency types, and a textual/API-model diff of public declarations. API Extractor is explicitly designed to expose accidental TypeScript exports and produce reviewable API reports; `cargo-public-api` provides the same general idea for Rust. The purpose of the metric is to make growth intentional, not to reward the smallest number. **Established tooling practice, current 2026.** citeturn14search0turn14search6turn7search3

## Data, schema, and evolution contracts

A schema is a contract even when no public customer sees it. The important distinction is not “external API versus internal API”, but **whether producer and consumer can differ in version, implementation or deployment time**. A database migration read by yesterday's binary, a queued event replayed three months later, and a mobile client lagging four releases behind all create compatibility obligations.

**Backward compatibility should be evaluated against observable behaviour and old consumers.** Google's AIP-180 explicitly treats APIs as contracts and warns that observable outputs can acquire compatibility significance, while SemVer defines incompatible public-API change as a major-version concern. The exact compatibility rules are protocol-specific: Protobuf, for example, says not to reuse field numbers, recommends reserving removed fields/numbers, warns against changing field types, and advises against adding required fields. **Established practice/specification, 2019–2026.** citeturn1search2turn14search4turn6search0

Versioning should therefore be a **last line of defence for intentional incompatibility, not a substitute for compatibility discipline**. Google AIP-185, approved in 2024, describes explicit major API versions and requires deprecation before certain removals in its versioning models. The exact deprecation window in that document is Google-specific rather than universal; an audit should instead ask whether the project has *some explicit supported-consumer window* and evidence before removal. **Established Google-specific guidance, 2024.** citeturn14search2

A particularly valuable distinction is **schema compatibility testing versus consumer-driven contract testing**. A schema diff answers, “Did this definition make a structurally incompatible change under this protocol's rules?” Buf, for example, can compare Protobuf APIs using source-, package- or wire-oriented compatibility policies. Consumer-driven testing answers a different question: “Does the provider still satisfy the concrete interaction that a real consumer relies on?” Pact describes this as contracts generated from consumer expectations and deliberately recommends constraining only what that consumer actually relies on. Neither substitutes for semantic product tests. **Established tooling/literature, current 2025–2026.** citeturn6search2turn6search1turn6search9

A schema audit should distinguish **intentional layer-specific DTOs** from **DTO drift**. The problem is not that `ApiUser`, `User` and `UserRow` are separate; that separation may honestly model different contracts. The finding is three independently hand-maintained near-identical shapes where a field becomes required in one, optional in another and silently dropped in a third, with no explicit adapter documenting the transformation. The preferred remedies are either a common generated schema where the semantics truly are shared or an explicit conversion function where they are deliberately different. This distinction is **audit opinion**; collapsing every layer onto one “universal model” is itself often an over-coupled contract.

Storage contracts deserve the same discipline. Fowler and Sadalage's “Evolutionary Database Design” argues that database changes should be represented as migrations, version-controlled and automated rather than performed as undocumented manual state. For an audit, the line-level smells are schema changes with no migration, destructive migration before readers/writers have migrated away from the old form, application code assuming a backfill is complete without enforcing it, and migration scripts whose relation to application versions is unknowable. **Established practice, 2016.** citeturn6search3

| Evolution criterion | Single-product application | Independently deployed / multi-service system |
|---|---|---|
| **Wire schema** | Validate the front-end/back-end and any external-client boundary. A common generated schema or an explicit adapter is often enough when deployments are coordinated. | Treat every independently deployed producer/consumer pair as a compatibility surface; automate schema diffs and retain old-consumer test coverage. Protobuf/Buf demonstrate protocol-aware compatibility checking. citeturn6search0turn6search2 |
| **Consumer-driven contracts** | **Audit opinion:** often optional for a single backend and frontend released together if schema validation plus integration tests already exercise the contract. | High-value when teams/services deploy independently and schemas alone cannot express the exact fields/interactions consumers depend upon. Pact is the canonical code-first example. citeturn6search1turn6search9 |
| **Events/messages** | Parse at ingestion and test stored/replayed samples if queues or durable events exist. | Check old-message replay, producer-first/consumer-first rollout, field evolution, enum evolution and lagging consumers explicitly. Compatibility requirements should follow the serialization technology rather than generic “JSON is flexible” assumptions. |
| **Deprecation** | Can be lightweight for private contracts, but old persisted data and old app versions still determine what can be removed. | Record owners/consumers, mark deprecation, observe remaining use where possible, and remove only under the supported compatibility policy. Google AIP-185 supplies one concrete model. citeturn14search2 |
| **Database/storage** | Migration-in-version-control discipline is essential even in a monolith because code and data evolve on different timelines. citeturn6search3 | Additionally require rolling-deployment compatibility, staged/expand-migrate-contract changes and explicit responsibility for cross-service data/event migrations. The staging threshold here is **audit opinion**, because deployment topology determines the requirement. |
| **Public versioning** | Often unnecessary for a private, lockstep API; compatibility can instead be maintained through coordinated releases. | Define compatibility and version policy explicitly. SemVer applies to versioned software public APIs; service APIs may use major interface versions or another documented policy. citeturn14search4turn14search2 |

A good line-level finding here is not “this API has no v2.” It is closer to: **“At `schema.proto:47`, field 6 was reassigned from `customer_id` to `account_id`; previously serialized messages can therefore be interpreted under a different meaning, contrary to Protobuf's field-number compatibility rule.”** citeturn6search0 Or: **“At migration X the old column is dropped while the preceding application version still reads it; the repository supports rolling deployment, so the storage contract is incompatible during rollout.”** The latter requires repository-specific evidence and is therefore judgment rather than a generic rule.

## Front-end contract rubric

Front-end contract quality is often underestimated because many mismatches still render “something”. The right standard is the same as for back-end code: props, context values, URL parameters, server-state objects and design-system components should advertise the states their implementation actually supports.

React's current documentation gives three useful baseline principles. Props are the normal explicit communication mechanism and are read-only inputs; context is powerful but explicitly easy to overuse; and controlled versus uncontrolled components are principally a choice about which component owns the source of truth. **Established React guidance, current 2026.** citeturn4search6turn4search4turn4search5

| Front-end criterion | What a finding looks like in code | Mechanical or judgment? | Severity guidance | Where it becomes over-engineering |
|---|---|---|---|---|
| **Required versus optional props** | `user?: User` but render immediately assumes `user.id`; `onSave?` but the only useful interaction requires saving; twenty optional props exist because different callers were not updated. | Prop type plus body analysis is highly automatable; whether “missing” has a coherent UI requires judgment. | **High** when absence causes runtime failure; **Medium** when it creates degraded/undefined UI. | Optional presentation props with an obvious visual default — `size`, `className`, optional decoration — are normal. |
| **Variant modelling** | `primary`, `secondary`, `danger`, `link`, `disabled`, `loading` booleans can be combined into unsupported states; a button/link component has optional `href` and optional `onClick` with no type enforcing which variant requires which field. Discriminated unions can make variant-specific props explicit. **Established TypeScript technique, current 2026.** citeturn2search5 | AST can count boolean/optional props and find candidate combinations. Validity is judgment. | **Medium–High** in a widely reused design system. | Do not turn independent booleans such as `disabled` and `aria-expanded` into a combinatorial mega-union merely because they can coexist. |
| **Prop drilling versus context** | A stable cross-cutting value passes unchanged through many non-consuming layers, or conversely a local value is placed in global context so consumers acquire hidden dependencies. React advises trying props/composition before reaching for context and notes that context is easy to overuse. **Established React guidance, current 2026.** citeturn4search4 | Prop-flow depth can be approximated mechanically; the appropriate ownership scope is judgment. | Usually **Low–Medium**; rises if hidden context dependencies make components impossible to use correctly in isolation. | Passing a value through a few components is not a defect; explicit data flow is a feature, not inherently “prop drilling”. |
| **Composition versus render callbacks** | A container has dozens of one-off props for every nested visual element instead of a compositional slot/children contract; alternatively a render callback exists merely to return static content and obscures a simple composition. React treats `children` as a standard way to receive nested content. **Established framework mechanism, current 2026.** citeturn4search6 | Candidate detection is possible; API ergonomics are judgment. | Mostly **Low–Medium**. | Do not replace a behaviour-bearing callback with composition when the consumer actually needs callback state/data. |
| **Controlled versus uncontrolled** | Component accepts `value` but also independently updates its own divergent value; prop changes do not update internal state; `defaultValue` behaves as continuous control; both parent and child believe they own the state. React describes controlled components as driven by props and uncontrolled ones as owning important state locally. **Established React guidance, current 2026.** citeturn4search5 | AST/state-flow analysis can flag `value` plus local state, but hybrid designs can be intentional. | **High** for data-entry components because user input can be lost or overwritten; otherwise **Medium**. | Legitimate APIs commonly support *either* controlled `value` or uncontrolled `defaultValue`; the defect is ambiguous switching or dual authority, not supporting both modes. |
| **Server-state contract** | `data?: T` plus `loading: boolean` and `error?: Error` permits contradictory combinations; “no data” is used both for initial loading, empty result and failure; stale data disappears during refetch because the state contract does not distinguish freshness from absence. | State-shape analysis is mechanical; expected UX is judgment. | **Medium–High** depending on whether incorrect state enables user actions. | A trivial one-shot screen does not need a formally encoded state machine if its few states are already unambiguous. |
| **Design-system API** | A foundational component accumulates an open-ended prop matrix, undocumented pass-throughs and polymorphic escape hatches so no caller can tell which combinations are supported; implementation-specific DOM/framework props leak as the primary abstraction. | Exported prop count/union complexity can be measured; usability and semantic combinations require judgment. | **High** when multiplied across the application; **Medium** otherwise. | Generic foundations necessarily expose flexibility. A highly constrained component for every stylistic variation can be worse than a small, orthogonal primitive API. |
| **Typed routes** | Route names/parameters are raw strings throughout application code; navigation to a renamed route keeps compiling; route handlers independently invent their parameter types. React Router's current type generation can provide route-specific parameter and loader/action/component types. **Framework-specific, current 2026.** citeturn4search3 | Strongly mechanical where the router provides generated types. | **Medium**, **High** when malformed navigation is common or user workflows depend on parameters. | Tiny applications with a handful of static routes may get little benefit from elaborate route-generation infrastructure. |
| **URL state parsing** | `searchParams.get("page") as PageNumber`; arbitrary strings become enums/IDs via assertions; parse/default/serialize logic is duplicated among pages; absence, malformed value and default are conflated. Route type generation does not by itself prove that the string `"17"` is a valid domain `PageNumber`; parse-don't-validate still applies. **Established principle; framework application is audit opinion.** citeturn5search0turn4search3 | Casts and duplicated parsers are searchable. Domain interpretation requires judgment. | **High** where URL state drives destructive/business operations; usually **Medium**. | Do not introduce domain wrappers around every cosmetic query string whose only consumer already accepts arbitrary text. |

The most important front-end distinction is between **syntactic typing** and **semantic parsing**. A router can know that a route contains a `projectId` parameter; that does not prove the received string belongs to the application's valid `ProjectId` domain. The route is therefore a boundary at which semantic parsing may still be appropriate. React Router's generated route types and the parse-don't-validate principle solve complementary problems rather than competing ones. citeturn4search3turn5search0

For server state, an audit should especially look for **implicit state machines masquerading as independent optionals**. A representation such as:

```text
data?: T
error?: Error
isLoading: boolean
```

may permit states the UI never intentionally designed, whereas an explicit conceptual model such as `initial | loading | success(data) | empty | failure(error)` states the variants directly. This is an **audit recommendation**, not a requirement to model every React component as a formal automaton; the discriminator earns its cost when the state-dependent fields or transitions matter.

## Agent-written contracts: evidence, failure patterns, and defences

The 2026 evidence supports **targeted extra scrutiny of agent-written contracts**, but it does **not** support the blanket claim that “agent code has worse contracts”.

The strongest direct evidence is TypeScript-specific. Lee, Hassan and Hindle's MSR 2026 study filtered real-world agentic and human TypeScript PRs and found that agentic PRs added `any` at a mean rate of 2.16 per PR versus 0.24 for human PRs — approximately nine times as many — and were also more prone to type assertions and non-null assertions. The study itself cautions about scope and task differences. **Measured emerging evidence, April 2026; TypeScript only.** citeturn15view0

Real-world PR studies also identify error handling as a recurring correction point, though not specifically `catch { return default }`. Watanabe et al.'s 2026 revision of a study of 567 Claude Code PRs across 157 repositories found 83.8% were merged; of the merged agentic PRs, about 54.9% were integrated without further modification and 45.1% received revisions. Among the 214 revised agentic PRs, 47.7% contained bug-fix revisions, and the authors describe examples where reviewers changed error handling so fatal failures propagated rather than being logged/continued. Crucially, the study also found the proportion merged without revision was similar for its human comparison set, so those numbers are **not evidence that agents uniquely require more revisions**. **Measured emerging evidence, 2026.** citeturn17view1turn17view2

A separate MSR 2026 study of 387 agentic PRs touching 945 build files found “lack of error handling” 63 times among its detected build-code smells, while also reporting that 824 of the 945 files introduced no detected smell before or after the agent change. This supports “inspect error handling” as an agent-audit hotspot, not “agent build code usually mishandles errors.” **Measured emerging evidence, 2026; build-code scope only.** citeturn16view7turn16view8

Broader evidence is mixed rather than uniformly negative. A 2026 study following 37,623 provenance-labelled PRs from five coding agents plus matched human contributors found post-merge results were strongly agent-specific: for example, Codex PRs in that dataset were reverted less often than the human baseline, while Devin PRs were reverted more often. The appropriate conclusion for an audit is therefore **inspect characteristic failure modes, not assign severity based on AI provenance**. **Measured emerging evidence, September 2026.** citeturn16view9turn16view10

Likewise, a difference-in-differences study of Cursor adoption reported a short-term velocity increase accompanied by persistent increases in static-analysis warnings and code complexity in adopting projects. It is useful evidence that automated quality gates should remain active as agent throughput rises, but it concerns one tool/adoption setting and does not isolate contract design specifically. **Emerging evidence, 2025/2026 preprint.** citeturn16view3turn16view4

The evidence status of the specific patterns in the research prompt is therefore:

| Agent-related pattern | What the 2025–2026 evidence actually establishes | Audit defence |
|---|---|---|
| **Loosening types to make code pass** | **Measured, but narrowly.** Agentic TypeScript PRs in the MSR 2026 study introduced `any` about 9× as frequently as human PRs and more often used assertions/non-null assertions. The paper interprets this as a type-safety risk; it does not prove every occurrence was introduced *in order to* make compilation pass. citeturn15view0 | Strict compiler settings; lint/baseline new `any`, unchecked casts and non-null assertions; prohibit escape-hatch increases without an explanation; review them especially near boundaries. |
| **Optional parameters added to avoid fixing callers** | **Not directly quantified in the agent studies reviewed here.** The TypeScript study analysed a broad set of type constructs but does not report a rate for semantic optionalisation of required parameters. citeturn15view0 | AST query for a required→optional signature change, then check body and call sites. Agent rule: “Do not make a required value nullable/optional solely to satisfy existing callers; fix callers or document the new supported absence state.” |
| **Catch-and-default fallbacks** | **The precise pattern is not separately measured.** Watanabe et al. provide empirical evidence of revisions correcting optimistic/incorrect error propagation; the build-code study reports a “lack of error handling” smell. Neither establishes a population rate for broad-catch-plus-default specifically. citeturn17view2turn16view8 | AST/lint empty catches, broad catches returning normal-looking sentinels and logging-and-continuing. Force an explicit comment/typed wrapper where degradation is intentional. |
| **Duplicated near-identical types** | **No direct agent-specific quantitative result in the 2025–2026 studies reviewed here.** It should therefore be treated as an audit hypothesis, not a measured “AI tendency”. The large AIDev dataset enables such studies but the dataset paper itself does not establish this claim. citeturn16view11 | Structural type-similarity reports; generated wire types; named mapping/adapters; ask whether duplicate shapes deliberately represent different semantics before deduplicating. |
| **Inconsistent error mechanisms across neighbouring files** | **Not directly quantified as such.** Real-world agent PR research does show human revisions for error handling and for adherence to project-specific conventions, which makes local inconsistency a sensible review target but does not establish a causal agent-specific rate. citeturn17view2turn17view3 | Build a repository-level inventory of throw/result/null/error-code styles by layer; flag outliers relative to semantic peers rather than demanding one mechanism globally. |
| **Overly complex type machinery plus escape hatches** | **Measured for TypeScript.** The MSR 2026 study found agentic PRs used a larger set of advanced type constructs and also more anti-pattern constructs such as assertions. citeturn15view0 | Review whether advanced generics/conditional types actually remove invalid states; simplify types that ultimately require assertions everywhere to consume them. |
| **Missing project-specific conventions** | **Measured in one Claude Code PR corpus.** Revisions frequently involved style, refactoring, documentation and project-specific rules; authors recommend encoding repository guidance. This is one tool/corpus, not universal. citeturn17view2turn17view3 | Keep repository contract rules machine-checkable where possible; provide agents with the project's exact error, DTO, parser and API conventions instead of generic “write clean code” prose. |

Two emerging pieces of evidence are particularly useful for the **defence** side.

First, Krishnamurthi and Flatt's 2026 controlled type-error experiment ran 2,400 primary trials and found that more detailed static type-error information generally improved agents' ability to repair the programs; typed feedback also performed better than giving only dynamic test failures in the studied setting. The authors explicitly call the results preliminary and limited to their experimental language/setup. The practical implication is nevertheless strong enough for an audit programme: **do not turn type/lint diagnostics off for agents to reduce friction; feed them the full diagnostic and require a real fix**. **Emerging controlled evidence, June 2026.** citeturn16view5turn16view6

Second, a May 2026 controlled study of persistent coding-agent rule files ran more than 5,000 Claude Code/Opus 4.6 executions around SWE-bench Verified and found, in its setting, that **negative constraints** such as “do not refactor unrelated code” were more reliably beneficial than generic positive directives. The authors explicitly restrict external validity to the tested agent/model/benchmark. This argues for agent rules phrased as enforceable contract guardrails — for example, “do not weaken a parameter from required to optional to silence a type error” or “do not swallow an error and return a success-shaped default” — rather than a long manifesto saying “design good APIs”. **Emerging controlled evidence, May 2026.** citeturn19view0

The larger AIDev corpus is useful background rather than a quality result: its 2026 dataset release contains 932,791 agentic PRs from five agents across 116,211 repositories, with a richer curated subset of 33,596 PRs from 2,807 repositories. It demonstrates that real-world agent-code mining is now possible at substantial scale, but the existence of the dataset is not itself evidence for any particular contract defect. **Dataset evidence, 2026.** citeturn16view11

The audit policy I would derive is therefore: **agent provenance raises the priority of mechanically checking contract-widening and compiler-silencing changes; it should not raise the severity of a finding. Severity should still be determined by the resulting contract.** That last sentence is an **audit opinion**, and it avoids turning early empirical evidence into an unsupported claim that AI-authored code is categorically worse.

## Mechanical detection and a consistent LLM-review protocol

Contract design is unusually suitable for a **two-stage audit**: mechanically generate suspicious surfaces, then use judgment to decide whether the declared and actual contracts contradict one another.

| Check | Good mechanical signal | What still needs human/LLM judgment |
|---|---|---|
| **Required/optional honesty** | AST inventory of optional/defaulted/nullable parameters; required→optional changes; optional value followed by immediate throw/assert; call-site frequency. Strict-null type checking helps. citeturn2search0turn3search0 | Whether absence is intentionally supported for external/unknown callers; whether the guard is a meaningful domain error rather than proof the signature is dishonest. |
| **Nullability** | Enable strongest practical null/optional settings; find non-null assertions and casts that immediately undo declared nullability. TypeScript provides `strictNullChecks`, `exactOptionalPropertyTypes` and related strict flags. citeturn2search0 | Whether `null`, omission and `undefined` actually represent different domain states. |
| **Boolean flags** | AST query for boolean parameters, multiple boolean parameters and literal `true`/`false` at call sites. | Whether the boolean is an obvious property or really selects a mode/strategy that deserves a name/type. Abseil's warning is a readability heuristic, not a ban. citeturn1search1 |
| **Positional ambiguity** | Long argument lists; adjacent arguments with the same primitive type; repeated literal-heavy calls. | Whether named arguments/options object would actually improve the language's ergonomics and compatibility. |
| **Overloads** | Compare parameter positions/names/types; detect overlapping/ambiguous resolution. | Whether overloads describe one conceptual operation. |
| **Hidden failure** | Empty catches; broad catches returning `null`, `false`, empty collection or default object; ignored `Result`/error values; promise rejection handlers returning success-shaped data. Go explicitly warns that errors still need to be checked however exposed. citeturn20search2 | Whether fallback is genuinely specified degraded behaviour. |
| **Error taxonomy** | Enumerate exception/result/code types by layer and endpoint; detect equivalent functions using radically different channels; inspect mappings to HTTP/gRPC codes. | Which failures are semantically equivalent; retryability; whether a lower-level cause intentionally belongs to the API. citeturn8search0turn8search8 |
| **Invariant candidates** | Repeated guard expressions; repeated normalization; same primitive used for several IDs; string comparisons against a finite status set; clusters of mutually dependent optional fields. | Whether introducing a type lowers total complexity and whether the invariant is stable enough to deserve encoding. |
| **Trust-boundary parsing** | Find deserialization APIs and trace first consumers; flag unchecked casts immediately after JSON/DB/SDK input; track raw map/dictionary/JSON types escaping adapter modules. | What the actual trust boundary is, and whether a deserializer/library already enforces the relevant invariant. |
| **Over-validation** | Clone/repeated-condition detection for the same guard across handler/service/repository layers. | Whether each entry point can really rely on an upstream parser; public APIs may legitimately defend themselves independently. |
| **Public surface** | Export/public symbol count and diff; wildcard re-exports; public declarations referencing dependency packages; API snapshots. API Extractor and `cargo-public-api` provide concrete examples. citeturn14search0turn14search6turn7search3 | Whether an exported symbol is intentionally supported and how many consumers exist. |
| **Schema evolution** | CI diff old versus new schemas; Protobuf compatibility tooling; generated-client compilation; missing migration detection. Buf is one concrete implementation. citeturn6search2 | Semantic changes a structural diff cannot see: changed interpretation, defaults, ordering, retries, side effects or authorization assumptions. |
| **DTO drift** | Structural similarity matching; field-name/type diff across API/client/storage DTOs; detect duplicate interfaces with mostly identical members. | Whether the types intentionally represent different contexts — indiscriminate deduplication is itself a contract mistake. |
| **Controlled UI state** | Component accepts controlled prop while mutating a second internal state; prop→state copying effects; simultaneous `value`/`defaultValue` misuse candidates. | Whether hybrid operation is deliberately designed and documented. citeturn4search5 |
| **Front-end variants** | Count optional/boolean props; identify mutually exclusive props used in branching; string literals that act as undocumented variant enums. | Which combinations are valid product states. |
| **Route/URL state** | Raw route strings, duplicated paths, casts from search params, unchecked numeric/enum conversions. Framework type generation can cover structural route contracts. citeturn4search3 | Semantic validity of the URL value. |
| **Agent-prone type escape hatches** | Diff count of `any`, non-null assertions, unchecked assertions/casts, ignore/suppress comments and loosened optionals. | Whether a specific escape is justified. The higher agent incidence is currently measured only for TypeScript, not a general law. citeturn15view0 |

The most important implementation detail is to **baseline rather than demand zero**. An old codebase may reasonably contain hundreds of legacy casts or exports. An audit can ask whether a subsystem has an unusually high density, whether new code increases the count, or whether escape hatches cluster at trust boundaries. This is **audit opinion**; it avoids generating thousands of low-information findings that conceal the handful of dishonest contracts.

For public APIs, snapshotting is particularly effective because it changes the review question from “did anyone happen to notice that this helper became public?” to “why did the public API report change?” API Extractor's report workflow is explicitly built around committing the API synopsis and failing validation on unacknowledged changes. **Established TypeScript tooling, current 2026.** citeturn14search6 The same principle applies to schema compatibility reports and generated API descriptions. citeturn6search2

### A constrained prompt for an LLM contract reviewer

An LLM reviewer should be required to **prove a mismatch**, because unconstrained requests such as “find bad API design” encourage preference-driven criticism. A workable review contract is:

```text
Scope: Review contract design only.

A contract is a function/method signature, type, error behaviour, module export,
component prop interface, route/URL representation, wire/event schema, or
storage format.

Do not report architecture/decomposition issues, generic style issues, or
security findings except validation/parsing at a trust boundary.

For every finding:

1. Give one primary file:line anchor at the declared contract.
2. State exactly what that line promises or permits.
3. Give supporting file:line evidence from the implementation, caller,
   parser/schema, test, or neighbouring equivalent API.
4. State the contradiction or accidental compatibility obligation.
5. Give one concrete caller-visible counterexample:
   "A caller may legally do X according to the declaration, but Y happens."
6. Classify the evidence:
   - mechanically provable
   - strong semantic inference
   - weak/style preference
7. Emit findings only for the first two classes.
8. Assign severity from consequence and blast radius, not stylistic preference.
9. Recommend the smallest contract-level fix; do not redesign the subsystem.

Specific guardrails:

- Do not flag an optional parameter merely because all current callers pass it.
  Flag it only if absence is advertised but not genuinely supported.
- Do not demand Result/Either instead of exceptions, or vice versa, merely from
  personal preference. Flag inconsistent or information-losing failure contracts.
- Do not recommend a domain type unless it prevents a repeated or consequential
  invalid state.
- Do not flag a barrel/re-export merely because it exists. Show accidental or
  unsupported surface expansion.
- Do not call duplicated DTOs a defect unless their relationship is accidental
  or they are drifting; intentional API/domain/storage representations may differ.
- Treat a cast immediately after untrusted deserialization as suspicious;
  determine whether runtime parsing occurred before reporting it.
- Treat catch-and-default as a finding only when the returned default is
  success-shaped and the contract does not deliberately specify degradation.
- For agent-written code, inspect any, unchecked casts/assertions,
  non-null assertions, newly optional parameters, ignored errors, broad catches,
  suppressions, wildcard exports, and duplicate local types. Do not increase
  severity merely because an agent wrote the code.

For each finding return:
{location, contract, evidence, counterexample, category, severity,
 confidence, smallest_fix, mechanical_rule_if_possible}.

If you cannot produce the caller-visible counterexample, do not report it.
```

The last constraint — **produce a caller-visible counterexample or suppress the finding** — is particularly valuable. It converts vague observations such as “this API has too many optional props” into falsifiable claims such as “the type allows `{kind:'link'}` without `href`, but the render branch unconditionally passes `href!` to the anchor.” That creates a finding a code owner can accept or reject from specific lines.

For consistency across reviewers, I would also require **two pieces of evidence for judgment findings**: the primary declaration plus one implementation, caller, schema, test, or semantic-peer line. Purely mechanical findings such as an incompatible Protobuf field-number reuse can stand on the schema and baseline diff. Severity should then be calculated independently from confidence: a low-confidence possible data-corruption issue should not be labelled “Critical” until the semantic evidence is established.

A practical audit metric can therefore separate four quantities rather than producing one opaque score:

**contract contradictions** (declared versus actual behaviour), **unsafe widening** (extra nullable/optional/exported/unchecked states), **cross-surface inconsistency** (semantic peers disagree), and **evolution risk** (today's change violates an older consumer/storage contract). That categorization is **audit opinion**, but it is more diagnostic than counting “API smells”.

## Language-specific interpretation

The criteria above are deliberately language-agnostic. The mechanisms used to enforce them are not.

**TypeScript.** Turn on the strictness that makes absence and escape hatches visible before judging the type design. Current TypeScript configuration includes `strictNullChecks`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `useUnknownInCatchVariables`, `noImplicitAny` and the umbrella `strict` family. `exactOptionalPropertyTypes` is particularly relevant to contract audits because the distinction between “property absent” and “property explicitly assigned `undefined`” can otherwise disappear. TypeScript's discriminated unions and `never` exhaustiveness checking are strong tools for finite state contracts. **Language-specific established practice, current docs 2026.** citeturn2search0turn2search5

For an agent-heavy TypeScript codebase, add delta checks for `any`, assertions and non-null assertions because those are the type constructs for which there is direct 2026 empirical agent evidence. Do not turn that evidence into a blanket ban: assertions at a proven low-level interop boundary can still be appropriate. **Emerging TypeScript-specific evidence, 2026.** citeturn15view0

**Python.** Do not read `Optional[T]` as “the caller may omit this argument”: Python's typing documentation defines it as a nullable type, while argument optionality comes from a default. Also remember that Python does not enforce annotations at runtime, so an HTTP/JSON boundary still needs actual parsing/validation even when the handler is annotated. Python additionally supports keyword-only parameters with `*`, which is a useful alternative to parameter objects when positional ambiguity is the real problem. **Language-specific established documentation, current 2026.** citeturn3search0turn20search0

Python error audits should favour a coherent exception hierarchy and preserve causal information where errors are translated; Python supports explicit exception chaining with `raise ... from ...`. That does not imply every expected domain alternative must be an exception: the audit question remains whether callers can reliably distinguish and handle the advertised outcomes. **Language-specific established documentation, current 2026.** citeturn3search2

**Rust.** `Result<T,E>` makes recoverable failure part of the signature, while `Option<T>` communicates absence without an error. The Rust Book explicitly presents `Result` for errors a caller can interpret and react to; `?` propagates the error while keeping it represented in the function's return contract. Rust therefore makes hidden-failure findings comparatively easy to formulate: a conversion from `Result` to a default/`Option` is a concrete place to ask whether information is intentionally being discarded. **Language-specific established documentation, current 2026.** citeturn20search1turn20search4

For library/public-surface audits, Rust also has tooling such as `cargo-public-api` that can enumerate and diff exported API. The principle is broader than Rust: public-surface regression should be machine-visible rather than discovered after consumers depend on it. **Current tooling, 2026.** citeturn7search3

**Go.** Go's idiom is neither exceptions nor an algebraic `Result`, but explicit error values. Rob Pike's 2015 formulation emphasizes that errors are values that can be programmed with — while also stressing that they still need to be checked. Go 1.13's wrapping model adds an important contract consideration: choosing to wrap and expose an underlying error so that callers can match it can commit the API to that underlying identity. A Go audit should therefore flag discarded errors, inconsistent `(value, error)` semantics and accidental exposure of implementation errors, not the mere repetitiveness of `if err != nil`. **Language-specific established guidance, 2015/2019.** citeturn20search2turn2search7

**.NET and other overload-heavy OO APIs.** Microsoft's Framework Design Guidelines remain useful for signatures: overloads should represent the same conceptual operation, equivalent parameters should keep consistent names/order, and APIs should avoid ambiguous overload sets. The guidance originates in the Framework Design Guidelines era and the online material has been maintained since; it should be treated as .NET-specific API-design guidance rather than a universal mandate for languages with named arguments, sum types or different dispatch models. **Established, language-specific guidance, originally 2008; online guidance maintained through 2023–2025.** citeturn9search0turn9search1

Across all of these languages, the invariant behind the rubric remains the same: **the declaration should make every supported caller behaviour easy to express, every materially unsupported state hard to express, and every failure or compatibility obligation that callers must react to impossible to mistake for ordinary success.** The syntax differs; the audit test does not.
