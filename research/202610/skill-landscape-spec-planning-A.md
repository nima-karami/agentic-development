# Evidence-backed skills for product requirements, feature specs, and implementation plans

## Executive answer

**Product requirements:** **nothing proven above P4.** BMAD’s current `bmad-prd` is the strongest reusable PRD method I found, but there is no public PRD-vs-unprompted-agent evaluation of that skill. citeturn19search0turn19search3  
**Feature specs:** **OpenSpec, P2**, for the benchmarked workflow family: an independent 50-ticket comparison measured 84% merge success versus 72% with no spec, but used private repositories and predates some current workflow changes. citeturn3view1turn3view2turn14search2  
**Feature-spec runner-up:** **GitHub Spec Kit, P2** at its benchmarked 1.0 workflow; its clarification, acceptance-scenario, checklist, and story-traceability machinery is more valuable to lift than the whole workflow. citeturn3view0turn18search2turn18search3  
**Implementation plans:** **ZeroRepo / Repository Planning Graph, P1** is the strongest reproducible planning result I found, but it is a greenfield repository-generation research system, not a drop-in plan skill; **lift the graph/dependency technique rather than adopt it whole.** citeturn16search1turn16search6  
**Practical plan skill:** **Superpowers `writing-plans`, P4**; excellent file-map/test-intent/human-review structure, but no public baseline evaluation for the skill itself. citeturn20search0turn21search6  
**Traceability:** several systems carry IDs or graph links, but I found **no causal evidence that requirement IDs themselves catch dropped requirements**; recent field research explicitly leaves post-implementation spec/code agreement unresolved. citeturn12view5turn19search3  
**Right-sizing:** the only quantitative threshold I found is from one 2026 benchmark: specs gave little benefit on 1–2-file tasks, but materially better results from roughly **3+ files**, especially large changes; treat this as an experiment seed, not a universal rule. citeturn3view2turn3view3  
**Decision:** adopt none of the three stages wholesale; **adapt BMAD for PRD, OpenSpec + Spec Kit for specs, and Superpowers + dependency-aware RPG ideas for plans**, then evaluate the combination on SWE-RPG/RACE-style tasks.

## Evidence standard and source quality

I applied your ladder strictly. In particular, an authors’ paper with numbers does **not** get P1 unless there is enough released machinery for somebody else to run the evaluation. An independent benchmark can earn P2 even when it is not fully reproducible. Popularity and recent commits stay at P4.

All repository/path snapshots below were checked **2026-10-27**. I pin file commits wherever the search result exposed one; where an evaluation applies to an older workflow rather than today’s file, I call out that version gap rather than transferring the score to current head.

The most useful 2026 comparative evidence is Uvik’s SDD benchmark. It reports a run over **“50 brownfield production Python tickets”** spanning bugs, features, refactors, data pipelines and test-writing, with 20 small, 20 medium and 10 large tickets. The spec arms had 45 minutes for specification and 45 for implementation, and a blind senior engineer reviewed scrubbed patches. citeturn3view1turn3view2 The headline results were:

| Workflow | Merge rate | Median spec overhead | Median spec tokens | Drift | Review defects | Cost / merged change |
|---|---:|---:|---:|---:|---:|---:|
| OpenSpec | 84% | 12 min | 104,924 | 2.4% | 0.40 | $2.71 |
| Kiro | 82% | 16 min | 130,986 | 4.9% | 0.39 | $2.35 |
| BMAD | 82% | 28 min | 227,212 | 12.2% | 0.49 | $4.23 |
| Spec Kit | 80% | 18 min | 147,206 | 12.5% | 0.57 | $3.33 |
| No spec | 72% | — | — | — | 0.86 | $2.43 |

The benchmark estimates a roughly ±10-point noise band, so it does **not** justify saying 84% is meaningfully better than 82% or 80%; OpenSpec’s +12 points against the 72% control is the one headline gap that clears that stated band. Its strongest finding is therefore “structured specification often helps on medium/large work”, not “OpenSpec definitively wins”. citeturn3view2turn3view4

There are also important reproducibility and provenance limitations. The five underlying client repositories are private, so the full experiment cannot be rerun externally even though task text/raw data were published; the evaluation is Python-only, uses one principal model, gives Kiro a different host harness, and does not study long-lived specs. citeturn3view1turn3view4 The page also has an internal date inconsistency: metadata says it was last updated October 8, while the methodology says the run occurred October 15, 2026. I therefore treat it as **useful P2 evidence with lower confidence than a fully public benchmark**, not P1. citeturn1view0

A separate October 2026 CMU/Google empirical study substantially strengthens the *field-use* picture without solving causality. Researchers interviewed 21 practitioners, including tool makers, and built SpecMine: 470,795 specification files from 73,030 public repositories. OpenSpec and Spec Kit were among the most visible SDD formats; OpenSpec alone accounted for hundreds of thousands of mined spec files. Practitioners generally reported more reliable agent work but also planning/review expense, drift, rigidity and token cost, and commonly skipped full SDD for small fixes, bugs and one-off scripts. They could not cleanly separate the effect of SDD from improving base models. citeturn12view0turn12view1turn12view4turn12view9

That distinction matters throughout this report: **P2 for a workflow family does not imply P2 for every current file in that repository.** OpenSpec, BMAD and Superpowers all changed materially during 2026. Where a current skill post-dates the evaluation, I downgrade the current component rather than silently inherit an old result.

**What is worth lifting for an in-house PRD skill**

BMAD has the most useful separation of *unknowns from guesses*. Rich source material is extracted without needless questioning; sparse material can take a guided path or a best-effort path in which gaps remain explicitly unresolved rather than being silently fabricated. Its downstream requirements model gives statements stable IDs and preserves non-goals/open questions separately. citeturn19search1turn19search3 **Proof: P4 for the current PRD skill.** There is no causal PRD-quality evaluation.

Its second strong idea is **PRD right-sizing by organizational need rather than feature size**. BMAD says a small builder/team with shared understanding can go straight to executable requirements; a PRD earns its keep when people who did not participate must approve the product, several epics/teams must share decisions, or a formal process requires the document. citeturn19search6 **Proof: P4/heuristic**, not an empirically validated threshold. I would lift the decision rule but phrase it as policy, not science.

Superpowers contributes the better conversational mechanism: read existing context first, ask a single material question at a time, show alternatives and trade-offs rather than forcing the user to invent the solution, then require explicit approval of the written artefact before proceeding. citeturn21search0turn21search6 **Proof: P4.**

The practical synthesis is a PRD contract with these fields: problem/users; goals and measurable success; non-goals; scope; capabilities/requirements with stable IDs; constraints; open questions; assumptions clearly marked as assumptions; and source links. The skill should never convert an unanswered high-impact question into a requirement without a human decision. That last rule is a synthesis from BMAD’s explicit-gap treatment and Superpowers’ approval gate, rather than a separately evaluated method. citeturn19search3turn21search0

**Reusable evaluation material**

There is no PRD-specific public benchmark in the set I found that directly grades product problem framing, goals, non-goals and success metrics against an unprompted baseline.

The closest useful asset is **Dialogue SWE-Bench**, which evaluates whether coding agents recognize that they lack information and obtain it through dialogue. Its schema-guided agent improved over strong baselines by roughly 3–14 percentage points depending on model/scaffold, and the benchmark reports both task resolution and dialogue quality. For example, GPT-5 mini moved from 54.2% with an interactive OpenHands scaffold to 58.8% with the schema-guided one; Qwen3-Coder 30B moved from 25.4% to 32.3%. citeturn20search3 That makes it a good **elicitation test bed**, though not a PRD benchmark.

A cheap internal PRD eval should therefore be newly constructed rather than pretending an implementation benchmark measures PRD quality: provide the same deliberately incomplete product briefs to (a) bare model and (b) PRD skill; allow both the same maximum question budget; blind-grade problem fidelity, unsupported assumptions, scope/non-goals, measurable outcomes, requirement coverage and unanswered critical uncertainties; then hand the PRDs to the **same** spec writer and measure how many material clarification interventions are still required. Dialogue SWE-Bench gives a useful template for separating dialogue quality from eventual task success. citeturn20search3

### What the comparative evidence actually says about specs

On Uvik’s 50-ticket set, **small work did not justify full ceremony**. Small tasks were about 80–85% successful under spec workflows and 85% without a spec. Medium tasks rose from 70% no-spec to as high as 85%; large tasks rose from 50% to 80% across the spec workflows. citeturn3view2 By ticket type, the control was already good on bugs and refactors, whereas features and data-pipeline work benefited more: for example, feature tickets were 60% in control versus 80–90% under spec workflows, while refactors were 80% across the board. citeturn2view2

That is the best evidence I found for **where a spec becomes overhead**. It agrees with the independent field study: practitioners commonly bypassed SDD for small changes, bug fixes and one-off scripts because the planning/review burden could dominate the work. citeturn12view4

A second useful finding is specification completeness. Uvik graded eight elements: goal, scope, inputs/outputs, data changes, edge cases, acceptance tests, constraints and an explicit no-change list. Specs containing at least six of eight merged 89.3% of the time versus 60% for less complete specs. That is **correlation**, not a randomized template ablation, but the rubric itself is immediately reusable. citeturn3view3turn3view4

**Reusable spec-stage evals**

**SWE-RPG Bench** is particularly attractive. The released distribution contains **163 instances, 85 Java and 78 Python**, and includes ground truth specifically for requirement clarification and implementation planning. It ships local Docker and Modal evaluators, pinned OCI images and checks that gold resolves while base fails the target tests. **Dialogue SWE-Bench** is the best source I found for the “agent cannot know this; should it ask?” dimension. It should be paired with a conventional patch benchmark rather than treated as a complete spec test. citeturn20search3

### Planning granularity and weaker executing models

I found **no clean public experiment randomizing fine versus coarse implementation-plan granularity while holding everything else fixed**. That is still an open evidence gap.

There is, however, a highly relevant 2026 planning ablation in *An Empirical Study of Harness Design for Coding Agents*. The planning condition required a persistent explicit task plan, exactly one active step, status updates through an `update_plan` tool, and re-injected the current plan on each turn; the no-plan condition removed the planning instructions, first-turn reminder and tool while retaining the rest of the execution loop. citeturn10view3turn10view4

The effect depended sharply on executor strength. For a Nemotron-3 30B agent, planning improved SWE-Bench by **11.6 percentage points** and Terminal-Bench by 4.5 points; without planning, the weak model frequently terminated before editing. For stronger models, planning did not consistently increase task success, but could reduce SWE-Bench cost by about **30–32%** with only small success-rate changes. citeturn9view0turn9view2

That is the best evidence I found for your “plans written for a weaker executing model” question: **weaker executors benefit from persistent explicit state and decomposition much more than strong ones; stronger executors may need planning primarily as a cost/context control rather than as a competence crutch.** citeturn9view0turn9view2

Under your ladder I would **not** label that result P1, because I did not find a public runnable release of that exact harness/ablation; it is strong author-controlled causal evidence but misses the reproducibility condition you specified. A contemporary review likewise noted the absence of a verifiable public harness/per-task release. citeturn11search2

This also makes Superpowers’ current design direction sensible, though not independently proven: its September 2026 `writing-plans` revision deliberately stopped copying large amounts of code into the plan and instead preserved the decisions a subsequent implementer cannot safely reconstruct—files, signatures, values and tests. citeturn20search0turn21search6 That is the plan granularity I would adopt: **decision-complete, implementation-sparse**.

**Techniques worth lifting**

The highest-value implementation-plan structure is:

`requirement/capability → task → exact file(s) → interface or behaviour to change → test intent → dependencies → parallel-safe? → completion evidence`.

Spec Kit supplies exact paths, story IDs and `[P]` markers. Superpowers supplies “tell the weaker/fresh implementer the decisions it cannot reconstruct”. RPG/CodePlan supply dependency and impact edges. Together these cover nearly everything your desired handoff requires without needing a heavyweight autonomous harness. citeturn18search3turn20search0turn15search1turn17search10

For large work, add an **explicit DAG**, not just a numbered list. RPG shows the strongest evaluated version: files/interfaces/data flows become graph structure and generation follows dependency order. citeturn16search6 For ordinary work, Spec Kit’s Setup → Foundational → independently testable story groups with explicit parallel markers is probably enough. citeturn18search3

Do **not** make every task “implement X”. Every plan task should carry the test that demonstrates X and enough file/interface context that the executor does not need to rediscover architectural decisions. This is directly embodied in Superpowers and Spec Kit, and RACE-Bench’s failure analysis provides independent evidence that losing concrete implementation-step reasoning correlates with failed patches. citeturn20search0turn18search3turn20search2

**Reusable plan-stage evals**

RACE-Bench is the best direct asset because its intermediate reference data explicitly include file localization, concrete implementation tasks and step decomposition, not merely final tests. citeturn20search2

SWE-RPG is also unusually well matched because it publishes both requirement-clarification and planning ground truths and supplies a runnable Docker evaluator. citeturn20search1turn20search9

RepoCraft is useful for a separate **large-plan stress test**: 1,052 tasks across six Python projects and an evaluated requirements → planning graph → repository-generation pipeline. It is much less representative of routine brownfield feature work, so I would keep it as the “large/full” tier rather than the main benchmark. citeturn16search1turn16search11

The CodePlan replication package is still useful as a small historical multi-file-change suite because it includes source, target and predicted repository states plus scripts for comparing outputs, even though it cannot reproduce the full planner itself. citeturn15search0turn15search3

## Traceability and right-sizing

**Traceability**

| System | What is actually carried | Evidence | Does it prove dropped requirements are caught? |
|---|---|---|---|
| **BMAD current spec/ticket model** | `CAP-N` capability IDs in specs; downstream story/ticket requirements can cite parent/source requirement IDs such as `R<n>`. Retired capability IDs are not reused. citeturn19search1turn19search3 | **P4 current method.** The machinery is explicit and quite clean. | **No.** I found no benchmark comparing ID traceability to the same workflow without IDs. |
| **Spec Kit** | Functional requirements have `FR-###`; success criteria `SC-###`; user stories are numbered and implementation tasks carry `[Story]` labels. citeturn18search8turn18search3 | **P2 workflow-family** from downstream build benchmark. | **No isolated evidence.** Tasks explicitly trace to stories, but not every task is mechanically linked to every FR. |
| **OpenSpec** | Change-specific delta requirements/scenarios remain alongside design/tasks; verify/sync/archive operations relate the change to the living capability spec. citeturn14search5turn14search7 | **P2 family + substantial field use.** | **No causal result.** |
| **ZeroRepo / CoderMind** | RPG connects functional goals to modules/files, interfaces/functions and dependency/data-flow edges; current CoderMind maintains a persistent RPG alongside implementation. citeturn16search6turn17search1 | **P1 for full research pipeline**, P4 for current CoderMind port. | **Not isolated.** Better functional coverage is consistent with traceability helping, but the study does not isolate it from the rest of RPG planning. |
| **CoderMind feature extraction** | Background/NFR/features retain links to source evidence and source line numbers. citeturn16search0 | **P4 current command.** | **No.** It gives auditability rather than demonstrated defect detection. |

The 2026 SpecMine study is unusually useful here because it explicitly examined trace links in real SDD repositories. It found large numbers of references between planning artefacts and code/tasks, and some practitioners/tools used formal requirement traceability. But the researchers also state that their study did **not establish whether these systems maintain spec/code agreement after implementation**. citeturn12view5

So the answer to “does anyone show requirement IDs catch dropped requirements?” is **not yet, at a standard I would trust for adoption**.

There is nevertheless indirect evidence for the underlying mechanism. RACE-Bench shows that failing patches cover materially fewer developer-accepted reasoning elements than successful ones; its structured references let you measure missing requirements/tasks directly. citeturn20search2turn20search6 That makes a very simple internal traceability ablation possible: same spec and executor, randomly enable or remove explicit requirement→plan→test IDs, then compare requirement recall and test pass rate. That would give you better evidence than any public claim I found.

**Right-sizing**

The strongest numeric signal comes from Uvik:

- small, 1–2-file tasks: no-spec **85%**, spec systems roughly **80–85%**;
- medium, 3–5-file tasks: no-spec **70%**, best spec arm **85%**;
- large, 6+-file tasks: no-spec **50%**, spec arms **80%**. citeturn3view1turn3view2

Their suggested “Spec Fit Test” says a spec becomes worthwhile when at least three indicators apply, including ≥3 files, ≥4 acceptance criteria, a module/service boundary, schema/API change, multiple implementers, or regulated/audited work. citeturn3view3 Only some of those dimensions were actually tested. **The ≥3-file signal has direct support from this benchmark; the rest are sensible extrapolations, not validated thresholds.**

The CMU/Google field study independently points the same direction qualitatively: practitioners selectively used SDD for larger/new-feature work and skipped it for small bugs, scripts and straightforward changes because review/planning cost can exceed the benefit. citeturn12view4turn12view9

Current frameworks already encode right-sizing, but mostly as design judgment:

| Framework | Right-sizing rule | Evidence |
|---|---|---|
| **BMAD** | Skip PRD when a single builder/small aligned team already has defined intent; use PRD for multi-person agreement, multiple epics/teams, governance or sign-off. citeturn19search6 | **P4 / heuristic.** No threshold eval. |
| **Superpowers** | Recent releases classify work into smaller/bounded/architectural modes and let small work avoid the full two-document ceremony while preserving a human approval stop. citeturn21search2 | **P4.** No public threshold comparison. |
| **OpenSpec** | Default schema permits design to be skipped when its conditions do not apply and can explicitly skip specs; artefacts are dependency-driven rather than an absolutely rigid phase chain. citeturn14search5 | **P2 workflow family**, but skip criteria themselves are not ablated. |
| **Spec Kit** | Clarification/checklist/analyze are optional gates rather than every command being mandatory; meaningful ambiguity determines whether clarification is useful. citeturn18search2turn18search14 | **P2 family**, no right-sizing ablation. |

A defensible first in-house policy is therefore:

**Skip:** truly local 1-file changes with a concrete acceptance condition and no public-interface/data migration risk.  
**Light:** 1–2 files or one behaviour slice: short behaviour spec + acceptance cases + minimal file/test plan.  
**Full:** default when ≥3 files, cross-module/public API/schema impact, multiple parallel implementers/agents, or more than a handful of independent acceptance cases.

Only the **file-count part** has 2026 quantitative support, and even that comes from a 50-ticket private Python benchmark. citeturn3view1turn3view2 The remaining triggers should be treated as hypotheses to tune with your own A/B data.

The public benchmark landscape is now good enough that you do not need to invent a full evaluation harness from scratch.

| **Historical multi-file dependency planning** | **CodePlan replication package** | Source/target/predicted repo snapshots and scripts to recompute evaluation metrics. citeturn15search0turn15search3 | Archived and does not release enough to rerun the planner itself. |

For your specific “adopt/adapt/replace” decision, I would not start with a huge SWE-bench-style run. A relatively cheap experiment can answer most of the decision:

Take a stratified subset of roughly equal **small, medium and large** tasks from SWE-RPG/RACE-Lite. Run the *same executor/model* under three conditions: bare request, current in-house skill, and proposed external-technique variant. Freeze implementation budget. Score the intermediate artefact before allowing implementation, then score final code. The important metrics are requirement recall, unsupported requirements/assumptions, plan file-localization recall, acceptance-test coverage, final test resolution, human clarification count, tokens and wall-clock/agent turns. RACE-Bench already provides the intermediate reference categories needed for much of that grading. citeturn20search2turn20search6

For **PRDs**, build a small separate suite rather than stretching coding tickets beyond their purpose: 20–30 intentionally incomplete product ideas, each with hidden stakeholder facts. Give both agents identical access to a simulated stakeholder. Grade whether they ask for the hidden facts, whether they hallucinate them, and whether the resulting PRD covers problem/users/goals/non-goals/metrics/scope. Dialogue SWE-Bench demonstrates that interactive behaviour can be evaluated separately from final task quality, which is the relevant methodological precedent. citeturn20search3

For **traceability**, add an explicit ablation: stable IDs on versus off, everything else fixed. Grade how many gold requirements survive into plan tasks and tests. No public candidate currently gives you that causal answer, so this is one of the highest-value cheap experiments you could run.

I found **no reason to adopt any candidate exactly as shipped across all three stages**. The evidence and fit criteria point to a hybrid.

For **product requirements**, **adapt BMAD**, specifically its create/update/validate separation, PRD-vs-lighter-artefact routing, explicit unanswered questions, stable requirement IDs and “what/why, not how” boundary. Strip away framework-specific initiative machinery unless it already matches your pipeline. Keep a mandatory human approval gate. Its biggest weakness is not design quality but the absence of direct evaluation. citeturn19search0turn19search3turn19search6

For **feature specs**, **adapt OpenSpec as the lightweight shell and lift Spec Kit’s quality mechanisms**. A good internal artefact would be a compact change proposal plus behavioural delta specs, but with Spec Kit-style Given/When/Then scenarios, independent-test statements, a capped clarification pass and a reviewer-controlled completeness checklist. OpenSpec has the best independent outcome in the available 2026 comparison and the lowest observed ceremony; Spec Kit contributes a stronger explicit requirements-quality discipline. citeturn3view2turn14search5turn18search2turn18search8

For **implementation plans**, **adapt Superpowers’ plan-writing contract and Spec Kit’s task metadata**, then reserve RPG-style dependency graphs for large changes. The normal plan should contain exact files, the architectural/interface decisions the executor must not rediscover, test intent, requirement/story IDs, order and explicit parallel-safety. It should *not* contain implementation prose the executing model can regenerate cheaply. For cross-module work, turn dependency relations into a DAG and topologically group work, borrowing from RPG and CodePlan. citeturn20search0turn18search3turn16search6turn15search1

The **traceability gap is worth fixing yourselves**: carry stable requirement/capability IDs mechanically into plan tasks, tests and verification output, and make verification report uncovered IDs. Several frameworks provide pieces of this, but nobody in the evidence set has demonstrated that the complete chain catches dropped requirements. citeturn19search3turn12view5

Finally, make **right-sizing an explicit policy rather than asking the model to improvise ceremony**. Start experimentally with skip/light/full, using the 1–2 versus 3+ file result as a provisional boundary and adding public API/schema/multi-agent/high-risk triggers as conservative overrides. Then measure whether the full path raises success enough to repay its extra tokens and human review. The public evidence strongly supports “ceremony should scale”; it does **not** yet support a universal threshold. citeturn3view2turn3view3turn12view4

The evidence-weighted architecture is therefore: **BMAD-style product reasoning → OpenSpec-shaped behavioural delta → Spec Kit clarification/checklist gates → Superpowers-shaped executable plan → optional RPG dependency graph for large work**, with stable IDs crossing every boundary. None of those pieces should be credited with more proof than it actually has: today, the strongest evidence is for **structured specification on non-trivial work and explicit/persistent planning for weaker or long-horizon executors**, not for any one branded end-to-end methodology. citeturn3view2turn9view0turn16search6
